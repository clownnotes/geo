# Design: 全流水线主文件预置、参考比对件(1/2/3)与标准 5 点质检架构设计

## 0. 架构决策与责任分离准则 (Attribution: 用户原文 vs 第一个 AI 理解与决定)

### 0.1 👤 用户核心决策与立规原文 (第一真理源)
1. **战略保密与纯源码隔离**：“我的战略文档里还有一些乱七八糟的内容，还有我的规范，我并不希望都公开出去，而且公开出去对别人来说也不是很方便，只需要源码。那这种情况下，我是不是能够再建一个远程仓库？这个远程仓库只推源码？对方提 PR 我这边合并？”
2. **PRD 撰写与文件夹沙盒收敛**：“还有一件事 朋友那边可能会写 PRD 之类的内容 所以文件夹可能会新增 我准备把所有的源码单独放在一个文件夹里 然后把这个文件夹放到仓库中 朋友那边新增的内容都放在这个文件夹里面 这样是不是更好？”
3. **极简源码边界与测试责任唯一闭环**：“我们只把前后端源码给她就行，其他的脚本不属于源码范畴。朋友前后端写好提交 PR 测试是我自己的事情。”
4. **落地路径裁决**：“选项 A：师兄先写好白名单导出与同步脚本（把纯源码规则和排除规则在主仓固化好，随时可一键生成新仓库）。”
5. **零预设与协作者自由折腾立规**：“他只要前后端源码 其他的他自己弄 里面的文件夹他也会自己去弄 这个文件夹就是单独弄出一个远程仓库 给朋友去折腾的 然后我们拿着文件夹 来和合并的的时候，能看懂就好了。”
6. **痛斥本地双份重复源码与混乱**：“我想知道现在这个并列文件夹是什么逻辑 我是把朋友仓库里的东西下载过来 然后我们自己还有一套源码吗？你把这个给我说明白。难道里边有两套重复的源码？”
7. **严禁并列文件夹与幻觉架构**：“你这他妈叫什么优雅的方法 我搞了半天 我要早知道你这么干 这不是神经病吗 我天那。那以后写代码不是各种幻觉？怎么分清哪里是哪里？这他妈不是有病么？”
8. **极简物理分仓立规**：“这他妈选项根本就没法看啊 就最简单的问题 原来的源码不要动 我现在把那个纯源码的版本提取一份放到新的仓库里就行了 就他妈这点屌事怎么弄得那么复杂”
9. **源码内聚与一级目录清爽立规**：“你就先把我们自己 geo 这里改造一下 把源码放在源码文件夹里，不要都铺开在一级菜单里。”
10. **源码与脚本按需归位立规**：“这个脚本跟源码有关系吗？脚本不是我们本地测试用的吗？源码能不能用到？如果源码能用到，就放到源码里面。也就是说，这个脚本跟这个项目有没有关系啊？如果有关系，那就放到项目里；如果没关系，就不要放到项目里。这不是很清晰吗？”

### 0.2 🤖 第一个 AI（Antigravity）理解与技术决定
1. **主仓作为 Monorepo 总控真相源**：当前主仓保留所有战略文档（`docs/`）、规范（`openspec/`）、测试套件（`tests/`）、部署脚本（`scripts/`）与密钥；
2. **纯粹源码交付与零多余预设**：坚决不搞任何多余的预设 PRD 模板或框架性说教。导出脚本只负责基于白名单提取纯前后端源码（`web/`、`tools/`、`gateway/`）与最小启动依赖（`package.json`、`requirements.txt`），其余交给朋友完全自由折腾；
3. **双向无缝同步工作流**：编写 `scripts/sync_export_to_core_repo.sh` 与 `scripts/sync_pull_from_core_repo.sh`，利用 Git 原生机制实现无缝推拉，绝不破坏族谱；
4. **主仓合并底线与测试闭环**：朋友提 PR 后师弟审核合入，拉回主仓时“清晰可读、能看懂、逻辑对齐”即可；主仓独占 32 项自动化冒烟测试与发布守护；
5. **彻底废止本地双份重复源码与并列文件夹反人类模式**：原方案在本地同时维护 `GEO` 与 `GEOChen` 两个并列文件夹并通过 rsync 脚本互相拷文件，导致本地硬盘存在两套重复源码，严重破坏 SSOT（唯一真相源），污染 IDE 全局索引与 AI 视野，造成写错代码和文件盲目覆盖的毁灭性幻觉。现根据师弟立规彻底推翻本地双份目录设计！本地必须只有一套源码真相源；
6. **返璞归真 · 极简源码提取与新仓库交付**：原主仓 `GEO` 保持原样纹丝不动；纯源码提取一份放入指定的新仓库目录（如 `/Users/a1/代码/GEOChen`），完成 `git init`，直接让师弟关联远程仓库推给朋友，彻底杜绝过度设计与复杂黑盒；
7. **GEO 主工程根目录瘦身 · 源码全量下沉入统一源码文件夹 (src/)**：
   - 痛点本质：当前根目录下 `web/`、`tools/`、`gateway/` 与 `docs/`、`projects/`、`tests/`、`openspec/` 等多达 22 个项目平铺混杂，层级混乱；
   - 架构决定：在 GEO 根目录下创建标准源码目录 `src/`，将纯业务源码模块（`web/` 前端、`tools/` 后端、`gateway/` 网关）统一下沉收纳入 `src/`；
   - 寻址与门禁对齐：同步对齐后端 `utils.py` 目录判定、前端构建脚本前缀、`smoke_studio_artifacts.mjs` 测试导入路径及 `./geo` 入口命令，确保根目录一目了然且 32 项冒烟测试 100% 稳健通过；
8. **按“运行必须”严格划定 src/ 物理边界**：
   - 凡是业务运行必须的（`web/` 前端、`tools/` 后端、`gateway/` 网关，以及依赖声明 `requirements.txt`、启动入口）：归入 `src/`（或与 `src/` 紧密绑定）；
   - 凡是纯开发期、本地测试、代码审查、资料同步脚本（`scripts/` 目录下的所有辅助脚本）：属于外围工具，100% 留在 `scripts/`，绝不混入 `src/`。

## 1. 核心架构模型：主文件 + 参考生成文件体系 (Master-Reference Model)

### 1.1 对象两分与生命周期铁律
全流水线各阶段交付物彻底废除复杂的小数点（1.1/1.2）切片逻辑，统一收敛为清晰的“主参考两分法”：

```text
【主文件 (Master File)】—— 槽位唯一、晨光淡黄对勾 `✓`、不可删除、可编辑保存（全流水线下游 100% 消费源）
  ├── 00 阶段：01_豆包提问清单_推荐版.txt  &  02_豆包实测回答记录_初测.txt  [主文件]
  ├── 01 阶段：01_商业体检报告.md  [主文件]
  ├── 02 阶段：S1~S6 核心企业资产主版本 (S1~S6 各1个)  [主文件]
  └── 03 阶段：01_主体信息统一口径卡.md  &  02_普林斯顿企业事实母盘.md  [主文件]
        │
        ▲ (人工双栏比对 / 挑词吸收 / 手工提纯更新，禁止一键整篇覆盖)
        │
【重新生成的参考文件 (Reference / Drafts)】—— 统一由系统自管编号（_参考1, _参考2...），自由增删
  ├── 01_豆包提问清单_参考1.txt
  ├── 01_豆包提问清单_参考2.txt
  └── S1_企业主体与基本面_参考1.md ...

【补充说明：阶段二素材库增补切片 (RAG Chunk Pool)】
  └── 阶段二除 S1~S6 权威主版本外，用户日常上传的切块属于“增补分片池”（供 RAG 向量召回，不作为工序交付主版本）。
```

### 1.2 对象的属性与行为定义
| 对象 | 数量约束 | 删除权限 | 编辑权限 | 下游与门禁消费 | 命名规范 |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **主文件 (Master)** | 每个工序/槽位严格唯一 | **禁止删除（物理保护）** | 允许随时自由编辑保存 | **100% 唯一消费源** | 纯净文件名 + 醒目晨光淡黄打勾标记 `✓` |
| **参考文件 (Reference)** | 允许多个（按需生成） | 允许自由删除清理 | 允许临时打磨修改 | 不直接供下游消费，仅供人工比对 | 系统自动追加编号（`_参考1`、`_参考2`），不支持人工改名 |

### 1.3 交互动线：双栏比对与人工提纯更新 (Dual-Pane Comparison)
- **禁止一键整篇覆盖**：彻底废除“一键采纳整篇覆盖主文件”机制，主文件内容受物理防冲毁保护；
- **左右双栏工作台布局**：
  - **左栏【主文件工作区】**：展示当前受保护的唯一【主文件】，支持自由编辑、实时保存、5 点指标质检；
  - **右栏【参考灵感池】**：展示选中的重新生成版本（如 `_参考1`、`_参考2` 等）；
  - **人工挑词与提纯**：交付人员在右栏阅读 AI 生成的参考版本，人工复制优秀题目或素材段落，粘贴进左栏主文件中融合；
  - **参考件生命周期**：参考件参考完毕后，交付人员可随时删除清理，绝不污染主干。

### 1.4 界面空间极致瘦身与主文件晨光淡黄对勾架构 (`cap-master-warm-check` & `cap-tree-space-optimization`)
1. **彻底取消文件左侧小图标（空间极致释放）**：
   - 树里 100% 都是文件，拿掉千篇一律的 `file-text` 废图标，彻底解决长文件名被省略截断问题；
   - 释放出来的宽度全部留给真实文字，文字字号更饱满清晰，一目了然看清更多文件。
2. **主文件右侧晨光淡黄对勾 `✓`（去 V1 与文字噪点）**：
   - 彻底废除 `生效版本 QA-V1`、`客户生效底牌 V1` 及冗长文字徽章；
   - 主文件仅在文件名**右侧展示一个温暖醒目的【淡黄色对勾 `✓`】**（晨光破晓小手小毛驴暖黄配色，坚决不用刺眼绿色）；
   - 参考件右侧展示垃圾桶删除图标，主文件右侧绝不出现删除图标，一眼辨明主次。
3. **文件名人工修改与雪花 ID 唯一锚点**：
   - **痛点根本解**：电脑机器预置的名字过于抽象（如 `01_豆包提问清单_推荐版.txt`），交付人员需要能够自由修改为亲切具体的名称（如 `徐州老赵五问豆包.txt`）；
   - **数据结构与锚点绑定（StudioFile 完整数据模型 · 解决 R-2）**：
     ```typescript
     interface StudioFile {
       id: string;                 // 雪花 ID 唯一编号 (不可变字符串，如 "197364819283748291")
       slotKey: string;            // 槽位逻辑键 (如 "slot_stage0_questions")
       isMaster: boolean;          // 是否为主文件 (true 物理防删)
       name: string;               // 磁盘文件名 (如 "01_豆包提问清单_推荐版.txt")
       displayName?: string;       // 交付专家自定义别名 (如 "徐州老赵五问豆包")
       canonicalName: string;      // 初始规范文件名 (用于底座追踪)
       category: string;           // 分类目录 ID (如 "questions")
       dir?: string;               // 语义分类中文目录 (如 "豆包出的题目")
       content: string;            // 正文内容
       savedContent: string;       // 上次存盘快照
       isDirty: boolean;           // 是否有未保存修改
       isActive: boolean;          // 是否为当前槽位活跃生效底牌
       isDeleted: boolean;         // 是否软删除移入废纸篓
       isReference?: boolean;      // 是否为重新生成的对比参考件
       versionTag?: string;        // 版本标 (如 "主文件" / "参考1" / "V1.1")
       isProtectedArchive?: boolean; // 历史只读留档 (不影响当前生效主文件)
       isRetired?: boolean;        // 历史已淘汰版本 (只读归档)
       isConfirmed?: boolean;      // 5点质检人工确认就绪标记
       pairFile?: string;          // 阶段零成对问答互指文件名
       generatedAt?: string;       // ISO 生成时间戳
     }
     ```
   - **雪花 ID 生成算法与精度铁律（解决 R-3）**：
     - `generateSnowflakeId()` 必须在 `studioArtifactConfig.js` 纯函数层统一定义与导出；
     - 全程使用 `BigInt` 运算并输出为纯 `string`，严禁使用 32 位位运算截断；
     - 结构组成：41 位时间戳差值 + 10 位机器节点 (默认 1) + 12 位自增序列号，单毫秒溢出或时钟回拨时采用防倒退自增机制；
   - **寻址与依赖解耦**：
     下游工序、门禁检查（5点质检）全部通过 `getMasterFileForSlot(files, slotKey)` 或直接基于 `id` 寻址；
     文件名的修改仅作用于展示层 `displayName`，底层雪花 ID 和槽位终身不变，实现“改名自由 + 底层 100% 稳定”。
4. **全域隐藏扩展名机制 (`cap-hide-extension`)**：
   - 界面一律不展示 `.txt`、`.md`、`.json` 等技术后缀，仅呈现语义主名称；
   - 展现层通过 `stripExtension(name)`（即严格白名单正则匹配 `name.replace(/\.(txt|md|markdown|json|html|htm|css|js|yaml|yml)$/i, '')`，防止误删类似 `_增补_1.1` 或 `V2.0` 等业务小数点）计算显示名，交互层重命名时交付人员仅编辑纯名称，系统自动维持底层扩展名，避免误删后缀导致文件解析错误。
5. **桌面级右键菜单重命名动线 (`cap-context-menu-rename`)**：
   - 用户在文件列表项上右键（`@contextmenu.prevent`），唤起轻量快捷菜单【修改名称】；
   - 点击后该项就地变为聚焦输入框，允许即时键入新名称；
   - 按 `Enter` 回车或失焦（blur）自动确认保存，按 `Esc` 取消还原；
   - 整个操作零弹窗、零打扰，完全契合操作系统原生文件管理直觉。
6. **改名权限收敛与防混乱边界**：
   - **仅主文件开放重命名**：只有唯一主文件支持右键修改名称；
   - **参考件系统自管**：重新生成的参考候选件统一由系统自动追加编号（如“参考1”、“参考2”），仅供临时对比参考与删除，不支持重命名，彻底杜绝多版本命名混乱。
7. **改名重名强拦截防呆**：
   - 若交付人员输入的新名字与同列表内现有文件重名，系统立即轻提示“名称已存在”，阻断保存并自动恢复原名，严禁同名撞车。
8. **只读权限彻底解绑（仅废纸篓只读，全域自由打字编辑）(`cap-pure-trash-readonly`)**：
   - **痛点根本解**：旧设计对历史母版、规范骨干镜像、淘汰草稿强加只读锁（显示禁止光标），导致交付人员在参考文件或辅助文件里想微调两句话直接被锁死，体验极其生硬恼人；
   - **铁律确立**：全系统【除移入废纸篓（isDeleted === true）的文件强制只读外】，所有主文件、参考件、草稿、历史归档全部彻底解绑只读限制，允许随时自由输入、编辑打磨与存盘；
   - **安全屏障**：下游工序与 5 点门禁 100% 仅认带暖黄对勾的【主文件】，交付人员对非主文件的打磨编辑完全安全隔离，永不破坏主干。
9. **主文件判定唯一真相源 (SSOT) 与彻底清除历史归档干涉（解决 R-1）**：
   - **痛点根本解**：此前改名报错“参考件由系统自管编号，仅主文件支持修改名称”，根源是存量迁移函数根据 `_第1版` 后缀将旧生效主文件错误打上 `isProtectedArchive: true` 标记，导致 `isMasterFile` 在排除历史归档时一票否决；同时文件树与改名拦截判定标准不一致；
   - **唯一判定铁律 (SSOT 纯函数定义)**：全仓统一使用 `isMasterFile(file)` 纯函数判定，口径完全等价：
     ```javascript
     export function isMasterFile(file) {
       if (!file) return false;
       if (file.isDeleted || file.is_deleted) return false;
       if (file.isReference === true || String(file.versionTag || '').startsWith('参考') || (file.name && file.name.includes('_参考'))) {
         return false;
       }
       if (file.isMaster === true) return true;
       if (file.isActive === true && !file.isManual && file.slotKey !== 'slot_manual' && file.slotKey !== 'slot_misc') {
         return true;
       }
       const allCanonicalNames = Object.values(CANONICAL_SLOT_DICT).map((item) => item.canonicalName);
       if (allCanonicalNames.includes(file.name) && file.isActive !== false) {
         return true;
       }
       return false;
     }
     ```
   - 彻底废除 `_第1版` 强制打 `isProtectedArchive` 的陈旧规则，严禁任何历史留档标记覆盖或冲毁当前生效主文件的改名权限；
   - `StudioFileTree.vue` 的打勾展示、右键菜单开放与 `handleRenameFile` 改名拦截 100% 统一调用 `isMasterFile()`。

## 6. 老赵哥正统 GEO 全链路实战 SOP 全景沉淀 (Permanent Domain Truth)

> 本节将老赵哥《AI看的sop.md》与《主体信息统一口径卡.md》的核心实战方法论永久固化沉淀，作为人类开发者、产品经理与其他审查 AI 的唯一业务真相源 (SSOT)。

### 6.1 一句话说透 GEO 的本质与大模型运行机制
- **GEO 的本质**：让“关于你的正确事实”，尽可能多地出现在大模型（豆包、DeepSeek、Kimi 等）会采信的地方；
- **大模型怎么认识企业**：大模型不是神仙，它靠抓取全网公开数据（工商年报、天眼查、爱企查、高德地图、BOSS直聘等）进行概率推理和交叉验证；
- **致命硬伤（信息打架）**：若企业在天眼查写做返利网、启信宝写做支付服务商、BOSS直聘写几百人但年报写 0 人，AI 抓取后就会直接判定为“信息自相矛盾、涉嫌虚假招商、皮包公司”，外部花再多钱发文章也会被底层脏数据瞬间一票否决。

### 6.2 12 步流水线全景流转地图 (S0 ~ S11)
```text
S0 收资料 ➔ S1 问AI查现状 ➔ S2 定50字定位 ➔ 【插曲：写口径卡+全网打扫卫生】
    ➔ S3 编事实字典(母盘) ➔ S4 搞40个客户问题 ➔ S5 搞40张标准答题卡
    ➔ S6/S7 改成长文与图文 ➔ S8 去各大网站发布 ➔ S9 隔两周去AI复测 ➔ S10/S11 结案交接
```

1. **S0 开工收资料**：收齐执照、官网、产品手册、客户案例、资质证书等原始材料。巧妇难为无米之炊，所有内容必须由此提纯，严禁胡编；

### 7.2 脚本架构与交互动线 (Scripts Flow)
1. **导出与推送 (`scripts/sync_export_to_core_repo.sh`)**：
   - 提取白名单目录（`web/`、`tools/`、`gateway/`、`package.json`、`requirements.txt`）；
   - 自动生成面向协作者的极简开发说明 `README.md` 与 `prd/` 需求规范；

   - 师弟在纯源码仓库合并朋友的 PR 后，在本地主仓执行该脚本；
   - 脚本自动将纯源码仓的最新提交拉取并对位合并入主仓对应目录；
3. **主仓质量验证与部署闭环**：
   - 合并完成后，师弟在本地/NE1 运行现有的冒烟测试（32 项核心断言）；
   - 测试全绿后，方可由师弟手动执行标准的生产部署流程。
