# Design: 全流水线主文件预置、参考比对件(1/2/3)与标准 5 点质检架构设计

## 1. 核心架构模型：主文件 + 参考生成文件体系 (Master-Reference Model)

### 1.1 对象两分与生命周期铁律
全流水线各阶段交付物彻底废除复杂的小数点（1.1/1.2）切片逻辑，统一收敛为清晰的“主参考两分法”：

```text
【主文件 (Master File)】—— 槽位唯一、绿勾标记、不可删除、可编辑保存（全流水线下游 100% 消费源）
  ├── 00 阶段：01_豆包提问清单_推荐版.txt  &  02_豆包实测回答记录_初测.txt  [主文件]
  ├── 01 阶段：01_商业体检报告.md  [主文件]
  ├── 02 阶段：S1~S6 核心企业资产主版本 (S1~S6 各1个)  [主文件]
  └── 03 阶段：01_主体信息统一口径卡.md  &  02_普林斯顿企业事实母盘.md  [主文件]
        │
        ▲ (人工双栏比对 / 挑词吸收 / 手工提纯更新，禁止一键整篇覆盖)
        │
【重新生成的参考文件 (Reference / Drafts)】—— 统一由系统自管编号（_参考1, _参考2...），自由增删
  ├── 01_豆包提问清单_参考1.txt
  ├── 01_豆包提问清单_参考2.txt
  └── S1_企业主体与基本面_参考1.md ...

【补充说明：阶段二素材库增补切片 (RAG Chunk Pool)】
  └── 阶段二除 S1~S6 权威主版本外，用户日常上传的切块属于“增补分片池”（供 RAG 向量召回，不作为工序交付主版本）。
```

### 1.2 对象的属性与行为定义
| 对象 | 数量约束 | 删除权限 | 编辑权限 | 下游与门禁消费 | 命名规范 |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **主文件 (Master)** | 每个工序/槽位严格唯一 | **禁止删除（物理保护）** | 允许随时自由编辑保存 | **100% 唯一消费源** | 纯净文件名 + 醒目晨光淡黄打勾标记 `✓` |
| **参考文件 (Reference)** | 允许多个（按需生成） | 允许自由删除清理 | 允许临时打磨修改 | 不直接供下游消费，仅供人工比对 | 系统自动追加编号（`_参考1`、`_参考2`），不支持人工改名 |

### 1.3 交互动线：双栏比对与人工提纯更新 (Dual-Pane Comparison)
- **禁止一键整篇覆盖**：彻底废除“一键采纳整篇覆盖主文件”机制，主文件内容受物理防冲毁保护；
- **左右双栏工作台布局**：
  - **左栏【主文件工作区】**：展示当前受保护的唯一【主文件】，支持自由编辑、实时保存、5 点指标质检；
  - **右栏【参考灵感池】**：展示选中的重新生成版本（如 `_参考1`、`_参考2` 等）；
  - **人工挑词与提纯**：交付人员在右栏阅读 AI 生成的参考版本，人工复制优秀题目或素材段落，粘贴进左栏主文件中融合；
  - **参考件生命周期**：参考件参考完毕后，交付人员可随时删除清理，绝不污染主干。

### 1.4 界面空间极致瘦身与主文件晨光淡黄对勾架构 (`cap-master-warm-check` & `cap-tree-space-optimization`)
1. **彻底取消文件左侧小图标（空间极致释放）**：
   - 树里 100% 都是文件，拿掉千篇一律的 `file-text` 废图标，彻底解决长文件名被省略截断问题；
   - 释放出来的宽度全部留给真实文字，文字字号更饱满清晰，一目了然看清更多文件。
2. **主文件右侧晨光淡黄对勾 `✓`（去 V1 与文字噪点）**：
   - 彻底废除 `生效版本 QA-V1`、`客户生效底牌 V1` 及冗长文字徽章；
   - 主文件仅在文件名**右侧展示一个温暖醒目的【淡黄色对勾 `✓`】**（晨光破晓小手小毛驴暖黄配色，坚决不用刺眼绿色）；
   - 参考件右侧展示垃圾桶删除图标，主文件右侧绝不出现删除图标，一眼辨明主次。
3. **文件名人工修改与雪花 ID 唯一锚点**：
   - **痛点根本解**：电脑机器预置的名字过于抽象（如 `01_豆包提问清单_推荐版.txt`），交付人员需要能够自由修改为亲切具体的名称（如 `徐州老赵五问豆包.txt`）；
   - **数据结构与锚点绑定**：
     ```typescript
     interface StudioFile {
       id: string;            // 雪花 ID 唯一编号 (不可变，如 "197364819283748291")
       slotKey: string;       // 槽位逻辑键 (如 "slot_stage0_questions")
       isMaster: boolean;     // 是否为主文件 (true 物理防删)
       name: string;          // 展示文件名 (交付专家可自由修改)
       canonicalName: string; // 初始规范文件名 (用于底座追踪)
       content: string;       // 正文内容
       savedContent: string;
       isDirty: boolean;
       isActive: boolean;     // 主文件恒为 true
       isDeleted: boolean;
     }
     ```
   - **寻址与依赖解耦**：
     下游工序、门禁检查（5点质检）全部通过 `getMasterFileForSlot(files, slotKey)` 或直接基于 `id` 寻址；
     文件名的修改仅作用于展示层 `name`，底层雪花 ID 和槽位终身不变，实现“改名自由 + 底层 100% 稳定”。
4. **全域隐藏扩展名机制 (`cap-hide-extension`)**：
   - 界面一律不展示 `.txt`、`.md`、`.json` 等技术后缀，仅呈现语义主名称；
   - 展现层通过 `stripExtension(name)`（即严格白名单正则匹配 `name.replace(/\.(txt|md|markdown|json|html|htm|css|js|yaml|yml)$/i, '')`，防止误删类似 `_增补_1.1` 或 `V2.0` 等业务小数点）计算显示名，交互层重命名时交付人员仅编辑纯名称，系统自动维持底层扩展名，避免误删后缀导致文件解析错误。
5. **桌面级右键菜单重命名动线 (`cap-context-menu-rename`)**：
   - 用户在文件列表项上右键（`@contextmenu.prevent`），唤起轻量快捷菜单【修改名称】；
   - 点击后该项就地变为聚焦输入框，允许即时键入新名称；
   - 按 `Enter` 回车或失焦（blur）自动确认保存，按 `Esc` 取消还原；
   - 整个操作零弹窗、零打扰，完全契合操作系统原生文件管理直觉。
6. **改名权限收敛与防混乱边界**：
   - **仅主文件开放重命名**：只有唯一主文件支持右键修改名称；
   - **参考件系统自管**：重新生成的参考候选件统一由系统自动追加编号（如“参考1”、“参考2”），仅供临时对比参考与删除，不支持重命名，彻底杜绝多版本命名混乱。
7. **改名重名强拦截防呆**：
   - 若交付人员输入的新名字与同列表内现有文件重名，系统立即轻提示“名称已存在”，阻断保存并自动恢复原名，严禁同名撞车。
8. **只读权限彻底解绑（仅废纸篓只读，全域自由打字编辑）(`cap-pure-trash-readonly`)**：
   - **痛点根本解**：旧设计对历史母版、规范骨干镜像、淘汰草稿强加只读锁（显示禁止光标 🚫），导致交付人员在参考文件或辅助文件里想微调两句话直接被锁死，体验极其生硬恼人；
   - **铁律确立**：全系统【除移入废纸篓（isDeleted === true）的文件强制只读外】，所有主文件、参考件、草稿、历史归档全部彻底解绑只读限制，允许随时自由输入、编辑打磨与存盘；
   - **安全屏障**：下游工序与 5 点门禁 100% 仅认带暖黄对勾的【主文件】，交付人员对非主文件的打磨编辑完全安全隔离，永不破坏主干。

## 2. 检查体系收敛（标准 5 点核心质检模型）
下游工序或全流水线门禁在判定上游工序主文件是否“真正就绪”时，统一实行 5 点状态检查（通过时点亮对应步骤的绿色指示灯，未通过时提供明确引导，不暴力白屏阻断）：

| 检查点 | 判定规则 | 典型场景（以 00 阶段为例） |
| :--- | :--- | :--- |
| **① 主文件存在性** | 槽位【主文件】必须物理存在 | `01_豆包提问清单_推荐版.txt` 与 `02_豆包实测回答记录_初测.txt` 存在（建档即预置） |
| **② 脱离初始空模版** | 正文内容必须已被实质性编辑，不再等于建档初始占位符 | 回答记录不再是 `说明：复制上方题目，直接前往豆包……` |
| **③ 真实字数达标** | 正文字符数达到业务有效信息最小门槛（防空转） | 回答记录正文字数 ≥ 50 字（包含豆包真实生成的长文本回答，SSOT 常量 MIN_MASTER_CONTENT_LENGTH=50） |
| **④ 消歧四要素齐备** | 品牌名、主体名、统一代码、核心官网在主文件中关联一致 | 题目与回答中准确包含当前客户真实品牌与主营行业，无占位符漂移 |
| **⑤ 人工确认就绪** | 交付专家在右侧 SOP 面板人工点击“确认完成并封版” | 交付人员人工通读质检无误后手动打勾，完成最终把关 |

## 4. 全工序零流程锁自由导航与文件事实探活架构 (`cap-zero-lock-navigation`)

### 4.1 彻底废除“机械点击锁”与原生 `confirm` 弹窗
- **痛点根本解**：旧设计依赖 `currentProjectData.probe_status === 'baseline_ready'` 判定，强迫用户必须点击“保存并封版完成阶段零”按钮才能修改后台字段；若未点该按钮，左侧菜单只要点击 01~07 任何工序，就会触发浏览器原生 `confirm(...)` 弹窗粗暴拦截并回退，体验极度恶劣且严重违反 RULES.md 4.4 禁令；
- **最高铁律落地**：
  1. **彻底拔除原生弹窗**：`web/index.html` 中的 `switchView` 与 `loadProjectDetail` 彻底删除 `confirm(...)` 弹窗与强行回退 `targetView = 'step-0-probe'` 逻辑；
  2. **00~07 全域自由平滑穿梭**：交付人员在左侧菜单可随时自由点击切换任意阶段，想看上一步就看上一步，想看下一步就看下一步，零阻断、零弹窗、零多余操作；
  3. **废止机械按钮绑定**：不再要求用户必须点“保存并封版完成阶段零”才算就绪。

### 4.2 “到底怎么才算有”：以主文件事实为唯一真相源 (File-as-SSOT)
- **自适应内容探活**：系统判定阶段零（或任何上游阶段）“算不算有答案”，100% 自动扫描主文件事实：
  - ① 槽位主文件 `02_豆包实测回答记录` 物理存在；
  - ② 正文脱离默认空模版；
  - ③ 有效字数达标（≥ 50 字）；
- **动态就绪**：满足上述条件，系统自动在内存中认定为就绪，无需人工多点一次按钮；即便未满足，也仅在页面顶部以柔和状态灯（指示灯）展现，绝不跳弹窗拦截用户的正常导航流转。

## 6. 老赵哥正统 GEO 全链路实战 SOP 全景沉淀 (Permanent Domain Truth)

> 本节将老赵哥《AI看的sop.md》与《主体信息统一口径卡.md》的核心实战方法论永久固化沉淀，作为人类开发者、产品经理与其他审查 AI 的唯一业务真相源 (SSOT)。

### 6.1 一句话说透 GEO 的本质与大模型运行机制
- **GEO 的本质**：让“关于你的正确事实”，尽可能多地出现在大模型（豆包、DeepSeek、Kimi 等）会采信的地方；
- **大模型怎么认识企业**：大模型不是神仙，它靠抓取全网公开数据（工商年报、天眼查、爱企查、高德地图、BOSS直聘等）进行概率推理和交叉验证；
- **致命硬伤（信息打架）**：若企业在天眼查写做返利网、启信宝写做支付服务商、BOSS直聘写几百人但年报写 0 人，AI 抓取后就会直接判定为“信息自相矛盾、涉嫌虚假招商、皮包公司”，外部花再多钱发文章也会被底层脏数据瞬间一票否决。

### 6.2 12 步流水线全景流转地图 (S0 ~ S11)
```text
S0 收资料 ➔ S1 问AI查现状 ➔ S2 定50字定位 ➔ 【插曲：写口径卡+全网打扫卫生】
    ➔ S3 编事实字典(母盘) ➔ S4 搞40个客户问题 ➔ S5 搞40张标准答题卡
    ➔ S6/S7 改成长文与图文 ➔ S8 去各大网站发布 ➔ S9 隔两周去AI复测 ➔ S10/S11 结案交接
```

1. **S0 开工收资料**：收齐执照、官网、产品手册、客户案例、资质证书等原始材料。巧妇难为无米之炊，所有内容必须由此提纯，严禁胡编；
2. **S1 AI 现状摸底（⚠️ 必须最先做）**：拿 5 个固定问题去豆包、DeepSeek 实测，看 AI 认不认识、认得对不对，保存截图基线。老赵哥实测邻里GEO时，豆包把其误判为“山东菏泽做团购的”和“做小丑笔记返利的”，若不先摸底，后续所有内容都将南辕北辙；
3. **S2 明确项目定位**：提炼 50 字核心定位（地域 + 帮谁 + 解决什么 + 坚决不做什么），删掉“领先、专业、一站式”等虚词，只留硬事实；
4. **【核心前置插曲：主体信息统一口径卡 + 全网打扫卫生】**：
   - **铁律**：“先修内，再铺外！改完之前绝不要去外部发文章投稿！”；
   - **为什么需要“认领”**：天眼查、爱企查、地图等页面是平台爬虫自动生成的野生页面，企业默认没有密码。交付人员必须提供执照完成实名“认领”，拿回管理权；
   - **怎么改**：把写好的标准业务简介替换上去，对齐社保口径（0人就老实写0人），把历史旧业务改掉；
   - **字数铁律**：短版 ≤50 字（地图与标签位专用，防截断），标准版 ≤120 字（征信与招聘简介主力，超字数平台报错）；
5. **S3 建事实母盘（六模块知识库）**：
   - 包含定位边界、产品事实、客户场景、优势差异、真实案例、外部背书 6 大抽屉；
   - **核心铁律**：这是给人类（交付顾问、写手、销售）看的查证字典！严禁直接把字典喂给 AI，防止 AI 学走“内部参考、待补充”等约束词；
   - **自检硬标准**：随机抽一个刁钻问题，5 分钟内能否在母盘找到答案依据、数据和链接；
6. **S4 建问题库（40 问地图与尺子）**：探索期 16 问 + 评估期 16 问 + 行动期 8 问；
7. **S5 建答案库（40 张标准答题卡）**：从 S3 母盘提取硬证据，生产 40 张标准问答卡（核心弹药库）；
8. **S6 派生图文 / S7 派生文章**：将答题卡改造成知乎、微信、百家号长文。文章是“字典词条”，供大模型随时抽取引用；
9. **S8 全网发布与信源互证**：投递知乎、垂直行业门户，多渠道用同一套口径互相佐证；
10. **S9 隔两周去 AI 复测**：用 S1 的 5 个问题再去问 AI，比对截图，查看大模型是否改口并推荐我们；
11. **S10 承接 / S11 验收结案**：电话微信入口畅通，交付资产打包归档。
