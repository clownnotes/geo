## 二、关键技术与交互决策裁决 [已达成共识]

1. **工程架构实现方式**：
   - **共识**：沉淀一套通用的 Studio 核心组件岛，由统一配置表驱动阶段 0～5。
   - **裁决理由**：遵循唯一真相源（SSOT）铁律，避免产生 6 套重复的编辑器、文件树和 Tab 管理代码，大幅降低维护成本。

2. **阶段一（商业转化诊断）设计**：
   - **共识**：左栏放报告、大屏与技术体检文件；中栏双 Tab（文字报告 Markdown + 老板视觉大屏 HTML 实时预览）；右栏 4 步标准化动线（真抓底座 -> 直出初稿 -> 复制润色 -> 定稿大屏）。
   - **裁决理由**：让交付人员既能在文字版去水润色，又能直观看到给老板展示的高转化大屏效果。

3. **阶段二（交钥匙官网交付）设计**：
   - **共识**：中栏只放底座文本代码编辑器（llms.txt / schema.jsonld / robots.txt / nginx.conf），交钥匙官网高保真整站通过点击按钮弹窗或新开独立浏览器窗口查看；右栏承载编译整站、验证大模型抓取友好度与导出源码。
   - **裁决理由**：保持中栏专注文档与代码修改，避免 iframe 挤占有限宽度，全屏预览体验更佳。

4. **阶段三（普林斯顿 9 因子高权威重构）设计**：
   - **共识**：中栏只显示母盘正文 Markdown；证据素材收集输入、唯一真相源清洗与冲突仲裁表、发前对照卡折叠收纳在右栏操作面板内。
   - **裁决理由**：突出母盘正文作为核心资产的打磨地位，右栏动线引导证据到真相的清洗流程。

5. **阶段四（矩阵分发与定稿发布）设计**：
   - **共识**：左栏按分发渠道列出交付稿件（头条稿.md、知乎稿.md、公众号稿.md等）；中栏专注 Markdown 在线精修；右栏承载「主问句与事实依据对照卡 + 勾选放行与一键复制发布」。
   - **裁决理由**：严守「草稿 ≠ 定稿 ≠ 可发」原则，交付人员对照右侧事实在中间逐篇改好再放行。

6. **阶段五（首轮监测与结案验收）设计**：
   - **共识**：左栏放周报/验收单/数据文件；中栏聚焦交付物预览（Tab 1: 4 维量化大屏与实测明细，Tab 2: 美化周报实时预览，Tab 3: 客户结案验收单对客格式）；右栏动线负责触发实时监测、归因分析与导出签发。
   - **裁决理由**：闭环对客结案，交付物一目了然。
