# Design: 管理端功能解答麦肯锡模型与阶段零重构

## 一、架构设计：麦肯锡 V-W-W-H 认知模型

所有功能模块的顶部解答与引导说明，一律遵循麦肯锡“金字塔原理（结论先行）”，自上而下严格划分为 4 个层级：

```
┌─────────────────────────────────────────────────────────────┐
│ 1. Value (价值结论 · 终局成果)                              │
│    做完能拿到什么交付成果？对业务有什么决定性价值？         │
├─────────────────────────────────────────────────────────────┤
│ 2. What (这是什么 · 定义与边界)                             │
│    通俗比喻定义功能本质，严格划清“管什么、不管什么”。       │
├─────────────────────────────────────────────────────────────┤
│ 3. Why (为什么做 · 痛点与避坑)                              │
│    不做的惨痛代价是什么？为什么不能跳过？                   │
├─────────────────────────────────────────────────────────────┤
│ 4. How (怎么去做 · 极简三步法)                              │
│    操作动线与人机分工闭环（①出题 ➔ ②真问 ➔ ③确认写入）。│
└─────────────────────────────────────────────────────────────┘
```

## 二、视觉系统：四色与排版尺寸规范

### 1. 色彩语义 Token

| 认知层级 | 语义定义 | 主题色 | Tailwind 类名 | 视觉特征 |
|---|---|---|---|---|
| **Value** | 价值与交付物 | 系统主色紫 | 底色：`bg-indigo-50/70`<br>左边条：`border-l-4 border-[#7c5bf5]`<br>文字：`text-indigo-950` | 顶层大卡片，强化确定感与业务结晶 |
| **What** | 客观事实与边界 | 冷调蓝灰色 | 底色：`bg-slate-50`<br>左边条：`border-l-4 border-sky-500`<br>文字：`text-slate-800` | 冷静客观，理清边界与概念 |
| **Why** | 警醒避坑与痛点 | 暖调琥珀黄 | 底色：`bg-amber-50/60`<br>左边条：`border-l-4 border-amber-500`<br>文字：`text-amber-950` | 提醒注意思考，警惕盲目施工 |
| **How** | 行动指引与动线 | 通路翡翠绿 | 底色：`bg-emerald-50/50`<br>左边条：`border-l-4 border-emerald-500`<br>文字：`text-emerald-950` | 畅通链路，明确 1-2-3 操作闭环 |

### 2. 颜色红线与边界
- **红色绝对保护**：红色（`rose-*` / `red-*`）保留给系统运行报错、网络断开、表单必填校验失败、不可逆删除等危险场景。**功能引导说明中 100% 严禁出现红色**。
- **浅底 + 侧彩条（Accent Line）**：严禁整块填充大饱和度彩块，统一使用微弱浅底色（`-50` 系列）搭配 `border-l-4` 彩条，克制高级，防止视觉疲劳。

### 3. 排版与尺寸规范
- **外容器**：`rounded-xl border border-slate-200 bg-white p-4 space-y-3`
- **价值卡片（Value）**：`p-3.5 rounded-lg border border-indigo-100`，标题使用 `text-xs font-bold`，带有高光徽章 `【核心交付成果】`。
- **展开说明三列/三段（What / Why / How）**：
  - 标题统一：`text-xs font-bold flex items-center gap-1.5`
  - 正文统一：`text-[11px] leading-relaxed`
  - 序号胶囊：`w-4 h-4 rounded-full text-[10px] font-bold inline-flex items-center justify-center`

## 三、实战打样：阶段零（先去豆包摸底）重构方案

### 1. 文案精编（五年级直白白话 · 对齐 plain-speak）

> **硬约束**（与 `.cursor/rules/plain-speak.mdc` 阶段零对照表一致）：
> - 界面只谈两件真东西：**问题清单**（要问豆包的几句话）与 **豆包答案存档**（问完并点过「确认写入」）。
> - **禁止**自造抽象交付物名充当主文案（如「底牌报告」「基线」「剧本」「探活」）。
> - How 三步必须与页内第 1/2/3 步一一对应，**禁止**把「落盘豆包结果文件」和「确认写入项目」混成一句。

```markdown
【核心交付成果】做完后，项目里会有：① 一份问题清单；② 一份已确认写入的豆包答案存档。
价值：后面写什么文章、补什么官网，都拿这份真实摸底当对照，不再凭感觉瞎写。

【这是什么】给豆包做一次快速「口语摸底」，不是正式建词库、也不改官网。
就像看病前先量个血压：挑 8~10 句客户行业里真人常问的话去问豆包。只管摸清它认不认识你们、推谁、有没有说错。

【为什么做】防止闭门造车。
很多客户以为大模型什么都懂；其实常把客户当竞品，或根本搜不到。不摸底就发文章 = 盲人摸象。先找出答错、漏答的地方，后面优化才有的放矢。

【怎么去做】本页出题 → 你去豆包真问 → 你点确认写入（约 3 分钟）
1. 出题：点下方按钮，生成并保存问题清单（8~10 题）；
2. 真问：拿着问题清单去豆包网页问一遍，把回答存成结果文件；
3. 写入：在第 3 步点「确认写入」——右上角才亮绿色「豆包答案已存进项目」。摸底才算完成。
管理台自己不会登录豆包。
```

### 2. 组件改造目标与边界
- **目标组件**：`web/step0-src/components/Step0Header.vue`（静态 V-W-W-H 引导区替换现有「按这个顺序做」整块说明）。
- **必须保留**：右上角双徽章（问题清单状态 / 豆包答案是否已存进项目）、存档编号、`该再测一遍` 等状态芯片。
- **`modeBanner` 不并入静态四层**：`modeBanner` 是动态「现在该做什么」（首轮 vs 再测一遍），继续由 `plainCopy.buildModeBanner` 驱动，放在 V-W-W-H **下方或 How 区旁侧**，不得用静态四层卡片吃掉角色/轮次差异文案。
- **双轨文案**：开发者 / 写文同事差异文案仍走 `plainCopy.js` + `useStep0.js`，本期只改引导层结构与用词，不改落盘契约。
- 编译生成新的 `web/assets/step0/step0.js`。

## 五、阶段零架构终极演进（方案 C：三栏式 IDE 专业交付工作台）

为彻底解决零散表单卡片松散、无法整体精修、交付物缺乏版本沉淀的问题，将阶段零作业台升级为对标现代 IDE（如 Qoder / VSCode）的**“三栏式专业交付工作台 (Delivery Studio)”**：

```text
┌─────────────────┬───────────────────────────────────────────┬──────────────────┐
│ 1. 资源管理器    │ 2. 多 Tab 文件编辑打磨区 (宽屏，人话纯文本) │ 3. SOP 指引与AI  │
│ (文件与交付物树) │ 顶部：[Tab 1 ×] [Tab 2 ×]                  │ (流程推进与生成)  │
│                 │ 面包屑：00_去豆包提问 > 01_豆包提问清单.txt │ 步骤 1：准备题目  │
│ 📁 00_去豆包提问 │ ┌──┬────────────────────────────────────┐ │ [✨ AI重新出题]  │
│  📄 提问清单.txt │ │01│ === 豆包实测提问清单 ===               │ │ 麦肯锡避坑指引   │
│  📄 回答记录.txt │ │02│ 客户：邻里GEO                         │ │ 步骤 2：去实测  │
│  📄 体检结论.txt │ │03│ [T1 品牌直搜]                         │ │ [📋 复制说明书] │
│ 📁 01_现状体检   │ │04│ "邻里GEO"是做什么的？                 │ │ 步骤 3：存入项目│
│                 │ └──┴────────────────────────────────────┘ │ [确认存入底牌]   │
│ [+ 新建] [- 软删]│ 工具栏：[💾保存] [↩️撤回] [📋一键复制]     │                  │
│ [🛡️查看软删待办] │ 底部状态栏：00_去豆包提问/01_提问清单.txt   │                  │
└─────────────────┴───────────────────────────────────────────┴──────────────────┘
```

### 1. 三栏详细功能与交互规范

#### (1) 左栏：资源管理器 (File Explorer)
* **目录范围严格隔离**：阶段零资源管理器 100% 仅展示属于阶段零的交付物资产，严禁混入阶段一、阶段二等无关阶段的目录。
* **按交付物种类归类（方案 A）**：
  * `📁 豆包出的题目/`：存放历次生成的题目文件（如 `豆包题目_第1版.txt`、`豆包题目_第2版.txt`、操作员手建的专项题等）。
  * `📁 豆包实测回答/`：存放去豆包真机实测后粘贴回来的回答记录（如 `豆包回答记录_首轮.txt`、`豆包回答记录_复测.txt`）。
  * `📁 阶段零体检结论/`：存放四维大模型健康度判定结论单（如 `豆包体检结论_最新.txt`）。
* **手风琴独占聚焦交互 (Accordion Focus)**：
  * 用户进行某类操作（或点击右侧步骤、或触发生成）时，该分类文件夹**自动展开**，其余文件夹**自动收起最小化**；
  * 确保操作员视线高度聚焦在当前正在作业的交付物上，界面干净清爽。
* **版本递增生成机制（绝不覆盖历史）**：
  * 每次点击 `[✨ AI 重新按资料出题]`，系统自动以 `豆包题目_第N版.txt` 形式**追加新文件**，并在中间打开新 Tab；
  * 彻底杜绝覆盖老文件，完好保留专家精修心血，支持随时跨 Tab 快速对比不同版本。
* **文件操作**：支持点击文件打开 Tab；支持新增自定义文件；支持两级软删除安全保护。

#### (2) 中栏：多 Tab 编辑打磨区 (Editor Studio)
* **多 Tab 管理与黄金上限（最多 6 个）**：
  * **黄金 6 个上限**：顶部最多允许同时打开 6 个文件标签页，保证各尺寸屏幕均能完整显示文件名（不出现截断或烦人滚动条），符合人眼短期记忆负荷。
  * **超限弹窗提醒，绝不默默自动关**：当已打开 6 个标签且用户尝试打开第 7 个文件（或重新生成题目）时，系统弹出友好警告提示（琥珀色），由操作员自主决定如何处理，绝不替用户做主自动关掉任何老标签，彻底杜绝未保存成果丢失或视觉惊扰。
  * **一键 [关闭其他] 快捷操作**：标签栏右侧提供 `[关闭其他]` 按钮；点击后一键关闭其他已保存文件，但若有其他文件带未保存修改（`isDirty`），系统自动将其安全保留并弹窗提醒。
  * **关闭标签安全保护**：点击单标签上的 `×` 时，若该文件有未保存修改，系统拦截并提示先保存或撤回，防止误触导致劳动成果丢失。
  * **标签计数器与平滑滚动**：右侧实时显示 `已开数/6` 气泡；切换文件时当前激活 Tab 自动平滑居中滚入视野。
* **面包屑路径**：Tab 下方展示当前文件在项目中的层级位置（如 `00_去豆包提问 / 01_豆包提问清单.txt`），让操作员时刻清楚文件归属。
* **人话纯文本排版（拒绝粘性代码）**：
  * 在临时原型与生产阶段，均以**结构化、大白话纯文本**呈现（包含标题、分类、题目正文、考察目的），绝不把生涩的花括号 JSON 源码直接塞给交付专家。
  * 配备清晰行号（Line Numbers），字体为等宽阅读字体。
  * **换行排版对齐**：行高固定对齐，遇到长文本自动折行，保证多题目视觉规整。
* **编辑与防丢失控制**：
  * **直接打磨**：操作员可直接在此将 AI 生成的 60 分题目精修为 80 分的高质量交付物。
  * **[💾 保存修改]**：将编辑缓冲区数据物理落盘到本地项目，浏览器刷新绝不丢失。
  * **[↩️ 撤回修改]**：放弃当前未保存的修改，一键恢复到磁盘原文件内容。
  * **[📋 一键复制全部]**：直接提取当前打磨好的纯文本内容，供操作员秒级粘贴到豆包网页中提问。
* **底部状态栏 (Status Bar)**：显示文件物理路径、行数/字数、编码与保存状态（已保存 / 未保存修改 ●）。

#### (3) 右栏：SOP 指引与 AI 协同区 (Workflow & Copilot)
* **流程指引驱动**：展示当前阶段的 1-2-3 步骤（准备题目 ➔ 豆包实测 ➔ 存入项目）。
* **AI 能力触发**：在步骤 1 提供 `[✨ 重新按客户资料自动出题]`，生成的题目直接载入中间编辑器。
* **三栏自动联动**：
  * 点击步骤 1，中间自动打开并高亮 `01_豆包提问清单.txt`；
  * 点击步骤 2，中间自动打开并高亮 `02_豆包回答记录.txt`；
  * 点击步骤 3，中间自动打开并高亮 `03_阶段零体检结论.txt`。

## 六、企业交付资产两级软删除安全机制（生产待办）

为防止操作员在交付过程中误删重要语料或关键诊断文件，确立以下安全机制：

1. **前台软删除（逻辑隐藏）**：
   * 交付操作员在前台点击“删除文件”时，系统弹出安全提示；
   * 确认后，该文件仅在前台资源管理器中隐藏，并在后台数据结构中打上软删除标记（如 `is_deleted: true, deleted_at: "..."`）；
   * 文件底牌数据完好无损，业务流程不受中断。
2. **后台系统管理员真删（物理抹除）**：
   * 在超级系统管理员后台（Admin Console），依然能完整查看到所有被标记为已删除的文件，并带有显眼的红色「已软删除」状态标签；
   * 只有当系统管理员在后台核验确认、并执行“永久清除”二次确认后，服务器才会从物理磁盘中彻底抹除该文件；
   * 管理员同时拥有“一键恢复”权限，可随时将误删文件恢复到前台。
3. **阶段推进**：
   * 当前临时前端先实现前台交互效果与软删除标记；
   * 生产后端上线时作为 P0 级权限安全底座全面落实。
