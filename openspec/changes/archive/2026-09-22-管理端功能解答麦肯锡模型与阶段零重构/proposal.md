# Proposal: 管理端功能解答麦肯锡模型与阶段零重构

## Why (为什么做)
1. **痛点与认知负担**：当前管理端（GEO交付控制台）的文字解答与操作引导较为晦涩，平铺直叙地堆砌了底层实现与操作细节（如“落盘文件”、“JSON”、“分两件事存入”），但缺乏“结论先行”的业务价值指引。
2. **缺乏金字塔结构**：操作者进入功能页面后，无法在第一眼获知“做完这个能得到什么交付成果”、“能实现什么核心目标”，必须逐字通读全篇后才能拼凑出意图，沟通和操作成本极高。
3. **颜色与尺寸缺乏语义规范**：界面中的各种背景卡片颜色缺乏统一标准（如浅绿、浅黄、浅蓝杂糅），缺乏视觉焦点，且没有将报错红色与引导说明严格区隔。

## What Changes (核心改动)
1. **确立麦肯锡 V-W-W-H 认知模型**：
   - **(a) Value 价值结论**：做完这个功能之后可以得到什么终局交付物，一句话总结其核心业务价值（结论先行）。
   - **(b) What 这是什么**：说明功能的本质是什么，用小学生能懂的比喻定义其业务边界（管什么、不管什么）。
   - **(c) Why 为什么做**：说明不做的严重后果（防踩坑与痛点），明确为什么不能跳过。
   - **(d) How 怎么去做**：说明怎么解决，采用极简三步闭环讲清具体操作流程与人机分工。
2. **制定四色与排版尺寸视觉规范**：
   - **第一段·价值结论 (Value)**：系统主色紫（Indigo `#7c5bf5`），大号重点卡片，左侧 4px 紫色边条，代表核心价值与交付产物。
   - **第二段·这是什么 (What)**：冷调蓝灰色（Slate / Sky），中号卡片，左侧 4px 天蓝边条，代表客观事实与概念边界。
   - **第三段·为什么做 (Why)**：暖调琥珀黄（Amber），中号卡片，左侧 4px 暖黄边条，代表警醒避坑与痛点原因。
   - **第四段·怎么去做 (How)**：通路翡翠绿（Emerald），步骤动线卡片，左侧 4px 翠绿边条，代表行动指引与闭环。
   - **严格红线**：红色（Rose/Red）绝对只用于系统异常报错与危险删除，严禁在功能解释中使用；杜绝全屏大彩块，统一使用浅底色 + 左侧彩条（Accent Line）。
3. **沉淀为全局标准方案**：
   - 撰写标准规范文档：`docs/specs/ui-feature-explanation-standard.md`。
   - 写入全局最高协议：更新 `AGENTS.md`，约束所有 IDE 与 Agent 严格遵守该标准。
4. **首发标杆打样**：
   - 以「阶段零：先去豆包摸底」作为实战改造对象，落地全新 V-W-W-H 结构与视觉规范。
5. **文案硬约束（与 plain-speak 对齐，不可破）**：
   - 阶段零只谈「问题清单」与「豆包答案存档」两件真东西；禁止自造「底牌报告 / 基线 / 剧本」等抽象主文案。
   - How 三步必须对应：出题 → 真问落盘 → 确认写入；不得混谈。
   - 动态 `modeBanner`（首轮 / 再测）保留，不并入静态四层卡片。

## Capabilities (新增或修改的对外能力)
- **文档规范能力**：沉淀统一的界面功能文案编写模型与颜色尺寸语义标准。
- **UI 组件标准**：定义功能解释的标准 DOM/组件规范。
- **交付体验提升**：阶段零及后续功能页按同一套「先说成果、再说边界、再讲避坑、最后动手」结构组织引导。

## Impact (受影响的部分)
- **文档层**：`docs/specs/ui-feature-explanation-standard.md`（新增，须引用 `geo-admin-ui-tokens.md` 主色）、`AGENTS.md`（更新标准规范章节）。
- **前端页面**：`web/step0-src/components/Step0Header.vue`、必要时 `plainCopy.js` / `useStep0.js` 引导文案。
- **明确不做**：不改 API / 落盘格式；不合并或删除右上角双徽章；不改 ProbeStep1/2/3 主操作区业务逻辑。
- **兼容性**：纯信息架构与 UI 引导层重构。
