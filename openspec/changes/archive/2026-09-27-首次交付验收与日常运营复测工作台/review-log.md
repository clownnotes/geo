## 二、关键技术决策与分歧裁决实录 `[已达成共识]`

### 决策一：阶段六与日常运营的架构关系
- **分歧**：原系统中阶段六直接呈现“商业运营结果（ROI 测算、客户续约预测、月度声量统计）”，导致交付阶段与运营阶段混淆。

### 决策二：首次交付的闭环深度与体验设计
- **探讨结论**：首次交付不能过度复杂，也不能只做成冷冰冰的静态清单，必须有立竿见影的“交付爽感”。
- **师弟裁决**：采用 **3 步闭环极简动线**：
  1. 资产盘点清单（母盘、40条答题卡、交钥匙官网、发布外链 URL）；
  2. 首轮核心 3 问真机抽测（问公司定位、评价与入口，粘贴豆包/DeepSeek回答，对比 S0 错误回答，直观呈现“已纠偏改口”）；
  3. 一键出具《首期工程移交与结项验收单》（好看大屏 HTML + 纸质打印签字版，双方交接签字，首期款结项）。
- **共识标记**：`[已达成共识]`

### 决策三：日常运营周期复测工作台的设计与挂载
- **探讨结论**：每周/每月运维人员拿 40 问去提问、粘回答、算 ROI，必须有专属的操作台。
- **师弟裁决**：在左侧「日常运维」中新增专属【周期复测与商业运营周报/月报】工作台，支持一键复制 40 问、批量贴回答案、依照 S9 五级信号自动判定、计算年化竞价节省与续约预测，并生成周报/月报。

### 二、必须补充的缺口

#### 🟡 新增视图 `mon-recurring` 未注册 `VIEW_META`（会导致功能完全不可用）

**实测现状**：

```
VIEW_META 共 23 个 view key
mon-* 现有：mon-weekly / mon-probing / mon-patrol / mon-deliverables / mon-decay / mon-crisis / mon-princeton
含 mon-recurring：False          ← 尚未注册
panel-mon-* 容器：7 个（同上，无 mon-recurring）
nav-mon-* 导航：7 个（同上）
```

而 `tasks.md` 7.3 要求「在侧边栏「日常运维」中新增导航入口「周期复测与商业运营月报」，**打通视图切换**」，
`design.md` 3.1 也只写到「挂载点：`nav-mon-recurring` -> `panel-mon-recurring`」。

**为什么这是阻断性问题**：`index.html` 的 `switchView` **第一行**就是硬兜底：

```js
function switchView(viewId, pushHash = true, opts = {}) {
  if (!VIEW_META[viewId]) viewId = 'overview';   // ← 未注册的 view 会被静默改写
  ...
}
```

**若不注册 `VIEW_META['mon-recurring']`，用户点击新导航时会跳到「客户档案与总资产看板」，
而不是新工作台** —— 功能表现为「点了没反应 / 跳错页」，且不会报错，排查成本高。

**为什么前几轮没遇到**：前五个变更都是**改造已有 view**（容器与 `VIEW_META` 条目均已存在，
只需改 `label`）；**本次是首个「新增全新 view」的变更**，因此必须显式注册。

**建议在 tasks 中补充**：

1. 在 `VIEW_META` 新增条目，例如
   `'mon-recurring': { group: 'daily', groupLabel: '日常运维', label: '周期复测与商业运营月报' }`；
2. 按需在 `hydrateView(viewId)` 中增加对应分支（若该视图需预加载数据）；
3. 确认 `expandSidebarGroup(group)` 能正确处理该分组；
4. 在 tasks 第 8 项验证清单中增加一条「点击侧边栏新入口能正确切换到目标面板」。
