## 2026-09-29 深度挖掘：第二份原合同《居间协议(处置）.docx》深度审计

### 1. 揭开真实业务真相
- **文件**：`/Volumes/资料 Mac320/居间协议(处置）.docx`
- **标题**：《不可撤销居间服务承诺书（居间合同）》
- **真实业务定位**：非一般商业不良资产处置，而是**“经乙方协调服务跟政府机构进行处置的虚拟货币”**（涉案虚拟货币司法变现/财政清收处置）。
- **两份合同的关系**：
  * **第一份（承诺书底牌版）**：极其野蛮、赤裸，来自河南郑州金水区模板，直接把合同定性为“见索即付”、“放弃一切抗辩权”、“不可撤销凭证”，且明目张胆写着走“个人账户打款”、“无需任何收款凭证”。
  * **第二份（朱壹强改写版）**：对方试图用“浙江省不良资产”作为包装外壳，但核心利益条款（按资产原值提 15.5%、次日催命打款、私账打款、数字货币、放弃追索权、莆田法院）依然沿袭了底层这套掠夺性逻辑。

### 2. 承诺书版新浮现的 4 大超高危刑事与民事陷阱
1. **【定性为“见索即付的无条件凭证”与“放弃一切抗辩权”】**：
   - 条款第 4、5 条逼迫甲方放弃任何法律抗辩权。一旦盖章，只要业务受阻或涉案被查，对方凭此承诺书即可直接向法院申请支付令或保全执行，公司形同签下不可抵赖的巨额欠条！
2. **【涉政府机构中介的刑事行贿/诈骗连带风险】**：
   - 条款写明“经乙方协调跟政府机构处置虚拟货币”。在司法处置中，任何私下“中介协调费”极易触碰行贿罪、受贿罪或利用影响力受贿罪的红线。一旦乙方被查，甲方公司将作为行贿/洗钱嫌疑主体被同步立案查处。
3. **【两小时内必须当日打款的极度垫资】**：
   - 第 2.2 条要求“每天处置任务完成后 2 小时内按约定付给乙方”。政府财政回款周期长，而对方要求公司两小时内先垫资把钱洗出去，完全是空手套白狼把风险全部转嫁给甲方。
4. **【无需凭证的地下钱庄式结算】**：
   - 第 3 条公然写明“乙方收取该款时无需办理任何收款凭证”。公账无法平账，股东走私账将面临职务侵占、偷税及反洗钱多重联合打击。

### 4. 师弟最高立规：【我们是甲方，只解决对甲方不利的】
- **核心定位**：彻底放弃任何中立或替乙方考虑的包袱，全盘站在甲方（蚂蚁多多）的绝对利益与商业安全上！
- **反转原则**：所有原合同中对甲方有约束、有惩罚、有风险的条款，全部重写为对甲方极其有利的霸权防御条款：
  1. **管辖权**：牢牢锁死在徐州市泉山区人民法院，绝不挪动；
  2. **提成基数**：必须是扣除甲方一切成本税费后的“净利润/净服务费”，未实际收到净利润一分不付；
  3. **付款前置条件**：必须先等发票或依法扣个税、资金完全在公账落袋、双方对账无误后才付款；未给合规发票，甲方有权不付且不承担违约责任；
  4. **违约与赔偿**：甲方逾期设宽限期且封顶；乙方若因虚假陈述或违法致使甲方受损，乙方必须全额赔偿甲方一切直接和间接损失（含律师费、差旅费、保全费）；
  5. **追索权与退款**：甲方保留无限追索权；业务一旦退款或出现瑕疵，乙方必须 3 日内全额退还已领提成；
  6. **展业自由**：非书面报备确认客户，甲方在全国及浙江享有 100% 自由展业权，与乙方零分成。

## 2026-09-29 核心业务真实场景锁定：政府罚没虚拟资产处置居间

### 1. 业务本质与双方定位对齐
- **业务场景**：处理**政府机关（公安、政法、法院、财政）罚没涉案虚拟资产**的司法处置居间中介。
- **甲乙双方合作机制**：
  * **乙方（朱壹强等中介）**：负责牵线引荐政府罚没虚拟资产处置业务机会；
  * **甲方（蚂蚁多多）**：受托承接技术处置变现，资金上缴国库/财政专户后获取合法处置服务费；
  * **处置后结算分润**：处置完毕、政府清算资金足额到账后，甲方从实际拿到的净服务收益中，跟乙方结算居间费用。
- **唯一最高红线**：**【甲方一定要绝对安全！】**

### 2. 针对罚没虚拟资产场景的 4 大绝密安全防火墙
1. **【绝对背靠背 (Back-to-Back) 结算】**：
   - 付款给乙方的不可分割前提是**政府财政处置服务费资金全额进到甲方对公账户并完成司法审计**；
   - 政府何时给、给多少，甲方何时分、分多少；政府若拖延或因案情扣减，甲方顺延支付且零违约责任；
   - 彻底封死任何两小时内打款、次日垫资打款的自杀式条款。
2. **【刑事反腐败与权力寻租防火隔离墙】**：
   - 严禁乙方以任何形式向政府官员、经办民警、司法人员进行任何形式的利益输送、行贿或回扣分赃；
   - 明文约定居间费仅为合法中介咨询报酬，若乙方有任何违法乱纪行为，纯属其个人犯罪，甲方概不负责并有权全额追索赔偿，彻底切割行贿共犯刑事风险。
3. **【反洗钱与先票后款税务护盾】**：
   - 坚决公对公人民币结算，绝不碰境外外币与 USDT 等任何形式的虚拟货币回流；
   - 必须先票后款（合规增值税发票）或依法扣除 20%~40% 劳务个税，未见发票甲方有权永久拒付。
4. **【司法异议与翻案追回 (Clawback) 机制】**：
   - 涉案虚拟资产若因案外人执行异议、司法再审、申诉退赔等原因导致政府追索已拨付服务费的，乙方必须在 3 个工作日内无条件、同比例退回已收全部居间款，甲方享有无限期追索权与法定抵销权。

**修法**：回退 design 第六节至"草案"，tasks 05 取消勾选，统一漏洞计数口径。

### B. 领域模型缺陷（design.md 第一节）

**B1. 缺失核心主体"政府/财政委托方"**。整份合同的付款绝对前提是"政府对甲方的财政服务费到账"，但 classDiagram 中**完全没有该主体**，银行仅作为 `participant` 出现在时序图。缺少该实体意味着：回款条件、审计终审、解付状态、追索触发**均无数据归属** → 背靠背条款无法被系统化表达。

**B2. `居间报备单` 与 `处置业务与回款` 的基数关系错误**。模型写作 `居间报备单 "1" -- "0..1" 处置业务与回款`。实际上一份客户报备可促成多个项目/多笔回款 → 应为 `1 -- "0..*"`。当前基数关系与"按实际回款计提 15.5%"的计费逻辑直接冲突。

**B3. `居间报备单` 字段与 design 第五节 R3"反跳单物理隔离补丁"不匹配**。R3 要求"限定到单一特定立案号与经办处室/专案子编号，未载明者视为未报备"，但报备单字段仅有 `项目编号/目标客户名称/报备时间/保护期终止时间/确认状态` —— **无案号、无经办处室字段**。规则与模型脱节，该补丁无法执行。

**B4. 缺失 `结算单` 与 `追回事件` 实体**。`结算单`（附件二，时序图第 6 步、R5 税后明细补丁依赖）、`追回通知书/Clawback 事件`（生死线 4、第五条依赖）在两个文档中被反复引用，却无对应领域对象 → 无字段、无状态机、无法校验。

**B5. 缺少"计费基数计算公式"**。`甲方净服务收益 (计费基数)` 是整份合同最核心的商业变量，但**没有定义公式**：是否扣除增值税、通道费、审计费、处置成本、政府分成、坏账？无公式 + 无举证责任分配 = 结算争议必爆点。这是本合同第 1 大商业风险，设计完全空白。

### C. 合规实质性缺陷（文本脱敏 ≠ 风险消除）

**C1. 标的物合法性未论证（最致命）**。design.md 第四节明确"业务表述全面脱敏：绝对不出现协调政府机构/政法委/公安等字眼"，并定性为"合法金融资产处置"。但：
- 删除字眼**不改变**业务实质。若向相对方隐瞒真实业务性质以获取信任并促成交易，反而可能构成《民法典》第 146 条"以合法形式掩盖非法目的"或第 148 条欺诈，**导致合同无效**，届时全部风控条款（含背靠背、追索权）一并落空。
- 境内虚拟货币相关业务活动被 2021 年十部委通知定性为非法金融活动。"处置罚没涉案虚拟资产"的合法性取决于**处置主体是否经法定程序取得授权**（办案机关依法定程序委托、是否经公开招标/政府采购、处置平台资质、款项上缴国库路径）。方案全程未触及该论证，而这是本合同"合法/非法"的分水岭。
**修法**：必须先出具《业务合法性论证意见》（授权文件、委托程序、上缴路径、甲方资质清单），再谈文本。**文本脱敏应表述为"合规表述"，而非风险消除手段。**

**C2. "刑事风险切割"条款在法律上不成立**。design 第一节/第六节第三条称"乙方违法纯属个人犯罪，甲方全额追偿"即可切割。对单位行贿、介绍贿赂均为独立罪名，单位及直接责任人员责任**不能通过民事约定免除**。当前设计给出了虚假的安全感，且该条款在司法审查中可能被作为"明知并预防性免责"的佐证。
**修法**：删除"切割"表述，改为"乙方承诺不实施任何违法行为+甲方内部廉洁与举报机制+违法时的合同解除与全额追偿权"，并明确**不承诺免除任何刑事或行政责任**。

**C3. "发票"与"个税代扣"机制重复且事实认定错误**。proposal.md 第 8 条称"未约定发票与个税代扣，导致甲方面临多缴 25% 企业所得税"，design 第四条将二者并列（"先票后款，依法代扣个税"）。事实是：
- 依国家税务总局公告 2018 年第 28 号第 9 条，**小额零星/自然人零星交易及依法代扣代缴个税的，可凭完税凭证+合同+付款凭证作为税前扣除凭证**，并非必须有发票。
- 二者是**替代关系而非并行关系**，方案未定义优先级、未定义"乙方办理临时税务登记按经营所得 vs 按劳务报酬所得"的路径选择。
- 因此"发票未到**永久拒付**且零违约"属过度保守，且与"代扣个税即可付款"路径冲突 → 执行时乙方可主张甲方阻碍付款条件成就（《民法典》第 159 条）。
**修法**：明确"（A）乙方自行开票 或（B）甲方代扣代缴个税并凭完税凭证入账"二选一的**唯一结款路径**及各自触发条件。

**C4. "第三方灵活用工平台"作为合规替代方案，与自身反虚开立场冲突**。design 矩阵第 4 行将"灵活用工平台合规完税代发"列为可谈筹码，但当前灵活用工平台代发是虚开发票/资金回流的高风险地带，与该方案"杜绝虚开发票"的核心目标相反。建议删除该筹码或附加严格的平台资质+业务真实性留痕要求。

**C5. "没收提成"与"向司法机关报案"用词不当**。design 第三节 R2 补丁称"违者没收全部未付及已付费用并向司法机关报案"。民事主体无"没收"权（应为"不予支付/追偿"）；以"报案"作为付款条件的要挟，存在被主张胁迫（《民法典》第 150 条）的风险。

### D. 逻辑漏洞

**D1. "永久保密 + 罚金 100 万元"与"违约金上限 3%/5%"体系冲突**。同一份合同内一处封顶、一处无封顶；且 100 万元罚金若与实际报酬（15.5% 提成）严重不成比例，法院可依《民法典》第 585 条调减；"永久"对非核心信息范围过宽。居间人为自然人、非甲方员工，亦无法适用竞业限制规则。

**D2. Clawback 3 日内全额退还 + 加计违约金，与自身"守约免责"筹码冲突，且可能被撤销**。design 矩阵第 8 行可谈空间为"守约免责（不可抗力致项目终止互不追责）"，但第六节第五条要求乙方在**政府追索（非乙方可归责事由）**时 3 日内全额退还并加违约金。二者直接矛盾；且将不可归责风险 100% 转嫁给自然人，存在显失公平被撤销的风险，同时大幅降低可签署性。
**修法**：区分"乙方过错致退赔"（全额+违约金）与"非归责事由致退赔"（按比例、给予 10~15 个工作日），并明确顺延规则。

**D3. 报备保护期机制存在三处未定义**：① 保护期自**报备日**起算还是甲方**确认日**起算；② 保护期届满但项目已签约在途（未回款）是否仍计酬；③ "甲方存量客户"与"乙方报备客户"的**判定标准与举证责任**未分配。这是报备制最容易被碰瓷的三个口子，恰是"反碰瓷"设计的核心，全部空白。

**D4. 收入确认与保护期顺延规则冲突**。design 第五节 R6 要求"签约后自动顺延至清算完毕"，与报备单字段 `保护期终止时间` 存在语义重叠 → 需明确顺延**仅适用于已在保护期内签约的在途项目**，否则保护期将无限延长。

**D5. "独家管辖"用语不规范**。协议管辖须与争议有实际联系且不得排除级别管辖；应表述为"双方协议由 XX 法院**排他（专属）管辖**"，并补充"不排除级别管辖规定的适用"。

**D6. 存量合同处理缺失**。design 第四节称要"废除《不可撤销承诺书》"，但全案只讲**新签**，未设计已签署原版文件/承诺书的**撤销、解除、失效确认与证据固定流程**。若旧文件已存在，新合同不能自动取代其效力。

**D7. proposal 三 Capabilities 承诺的"合同风控审计清单（红线指标）"在 design 中无对应交付物**，仅落盘了正文+2 个附件 → 对外承诺与交付物不一致。

**D8. 个人信息与涉案信息合规缺章**。居间人将接触"办案信息"（design 第六条），涉及《个人信息保护法》与涉案信息保密义务，但未约定数据处理者义务、禁止存储/复制/转发、行政处罚责任与通知义务。

## 4. 🟢 优化建议

**🟢-1（本报告最高优先级的架构建议）：建立条款单一数据源（SSOT）**
本次审查发现的 A1~A6 六组数值冲突，**根因不是笔误，而是同一批规则被重复书写在 proposal 第二节、design 矩阵、design 第六节、tasks 三处以上**。这正是"重复面条"的典型形态——只是当前载体是文档而非代码。

建议落盘 `rules/` 目录（为后续编码做准备）：

```
rules/clauses.ts     // 条款登记表：clauseId, 议题, 原版, 修订版, 底线, 筹码, 关联条款[]
rules/risks.ts       // 风险矩阵：riskId, 触发条件, 处置动作, 责任分配
rules/penalty.ts     // 唯一数值来源：费率/上限/宽限期/工作日定义/顺延规则
```

再生成 proposal / design / 合同 Word / 结算单模板。**任何数值只在 `penalty.ts` 出现一次**，文档由模板渲染。这样：冲突在编译期消失，且后续可纯函数化输出"合同风控审计清单"与"底线/筹码对照树"——这也正好补齐 D7 的交付物缺口。

**🟢-2 纯函数 & 无 DOM 依赖的前置设计约束**（为编码阶段预置）
若后续要做"条款合规校验器"，要求：
- 所有校验逻辑（比例区间、期限区间、管辖白名单、禁用语扫描）必须为**纯函数**：`validateClause(clause, rules) => Result[]`，不读 DOM、不读 window、不依赖当前时间。
- 时间计算（工作日顺延、保护期起止、Clawback 到期日）必须注入 `now` 参数，避免隐式 `Date.now()` 造成不可测。
- 期限一律统一为 `{value, unit: 'calendar_day' | 'working_day'}` 结构，从根上消除 A6 的"日/工作日"混用。

**🟢-3 Safari / Chrome 双内核兼容提示**（仅在未来有前端预览时适用）
- 中文字体（宋体/仿宋/黑体）在 macOS Safari 与 Windows Chrome 字体族回落差异较大，合同预览必须显式声明 `font-family` 候选链并内嵌/校验字体，否则 PDF 渲染会串版。
- 若使用 `Intl.NumberFormat` 渲染金额、`Intl.DateTimeFormat` 渲染期限，注意 Safari 对部分 locale/timeZone 参数的历史实现差异，必须显式指定 `locale` 与 `timeZone`，不可依赖默认值。
- 长表格（博弈矩阵 8~9 行 × 6 列）在 Safari 的 `table-layout: fixed` 下换行策略与 Chrome 不同，需显式设定列宽与 `word-break`。
- 若做 PDF 导出，注意 Safari 无原生 `print` 分页控制，`break-inside: avoid` 支持不完整。

**🟢-4 文档与代码的边界**：proposal/design 属"设计文档"，不含代码，**不存在破坏现有业务的风险**；上述兼容性事项不构成本阶段 Blocker，仅为编码前置约束。

## 三、问题分级清单

### 🔴 必须改（阻塞级，存在逻辑漏洞或法律风险）

1. **Clawback 退还期限与范围三处互相矛盾（最严重的 SSOT 违背）**
   - proposal 二.4：**3 个工作日**内**同比例**退还；
   - design 第七行矩阵：归责 **3 工作日**、非归责 **10 工作日**，**同比例**；
   - design 三 时序图 opt 分支：**5 个工作日**按比例退回；
   - design 六.第五条：**3 日**内（未写"工作日"）**全额**退还 + 千分之一违约金。
   四处口径不一（3/5 日、工作日/自然日、同比例/全额）。必须收敛为唯一表达式。
2. **报备保护期 SSOT 冲突**：design 一 对象模型"最长 6 个月"、矩阵第 1 行"最长不超过 6 个月"，但 design 五 R6 写"**3 个月**到期与回款周期错配"。6 vs 3 直接冲突。
3. **结算通道主体矛盾（主体不适格）**：乙方为**自然人**（身份证 + 实名借记卡），design 六.第四条却写"境内银行**公对公**"转账，proposal 也写"走境内人民币银行**对公**流水"。自然人无对公账户，条款天然无法履行。应改为"仅限乙方本人实名银行账户，**严禁指定第三方或他人代收**"。
4. **业务主体定义冲突（合同对象不闭环）**
   - design 一 对象模型：回款来自 `政府司法委托机关` → 财政拨付；
   - design 三 时序图：参与者为 `客户 = 浙江资产项目相对方`，第 4 步"甲方与**客户**签署《资产处置业务合同》"、第 5 步"**客户**回款打入甲方对公账户"。
   回款主体、缔约主体两处完全不一致。更严重的是 proposal 二.1 写"未报备客户甲方完全自主开拓"——若"客户"指办案机关，则"甲方自主开拓公安/财政"直接与"合法性前置（须由办案机关书面委托）"冲突。**必须先定义"客户"究竟是委托机关还是资产受让方/买家**，否则整个居间报备制的标的无法确定。
5. **脱敏准则与附件一要求自相矛盾（致命证据风险）**
   - design 四 准则 2：绝对不在合同文本中出现"协调政府机构""政法委""公安"等字眼；
   - 但 design 一 与 附件一 要求载明"对接机关全称（公安局/政法委/法院/财政局）+ 经办对接处室 + 特定案号"。
   两者不可共存。且要求以书面附件固定"具体经办处室 + 案号"，等于**主动制作权力寻租路径的书证**，一旦被查，该附件即成为利益输送的直接证据。建议：附件一改为**脱敏报备编号**（由甲方合规部门内部留档映射），对外文本不出现机关名与处室。
6. **脱敏准则与计费公式自相矛盾**：design 四 要求删除"虚拟货币"字眼，但 SSOT 公式与矩阵长期保留"链上 Gas 损耗/Gas 费"。要么承认涉币表述（则脱敏失效），要么把 Gas 归入抽象的"第三方技术处理费"（则公式需改）。二选一，不能并挂。
7. **"合法性前置"未落为合同条款（关键合规防线缺失）**。proposal 一把"依法取得办案机关书面委托"列为法定前提，但 design 六 九条正文中**没有任何**生效前提条款/陈述与保证条款。应至少补齐：① 合同生效条件为甲方已取得书面委托处置文件；② 乙方陈述并保证未向任何公职人员提供利益、未参与不当接触；③ 违反则合同自始无效且甲方免责。
8. **法律术语误用（多处，属于会被对方律师直接击穿的低级错误）**
   - "**排他专属管辖**"：我国"专属管辖"是法定概念（不动产、港口作业、继承），协议管辖不得自称"专属"。应改为"**协议管辖（排他性）**"。
   - "**罚金 100 万元**"（design 六.第六条保密）：罚金属刑罚，民事合同应为"**违约金**"。
   - "**没收提成**"（design 五 补丁 2、矩阵第 9 行、design 六 第三条）：民事主体无"没收"权，应为"**不予支付/已付部分返还**"。
9. **tasks 08 覆盖不全**（缺 R3 反跳单、R4 差旅垫资），却已勾选完成，属流程失真。

### 🟡 建议改（不阻塞，但会削弱条款效力或引发争议）

1. **违约金倍数不对等且可能超司法保护上限**：甲方逾期 0.01%/日（封顶 3%），乙方 Clawback 逾期 0.1%/日（=年化 36.5%），相差 10 倍。年化 36.5% 远超通常参照的 LPR 四倍，极可能被法院调减，"狠"反而落空；且与 proposal 二.7 自称的"违约金刚性对等化"目标自相矛盾。
2. **3% 封顶的基数未定义**（是未付居间费的 3%，还是合同总价的 3%？）。必须写明。
3. **甲方违约封顶、乙方"全额赔偿+律师费"的不对等**，在乙方主张格式条款时存在被认定"不合理加重对方责任"而无效的风险（尤其若乙方为自然人且无缔约优势证据）。建议双向均设合理范围或保留协商记录。
4. **"先票后款"标签不成立**：代扣个税路径根本无票（甲方出完税凭证）。标签应改为"先票或依法代扣（二选一）后付"。
5. **政府"扣减"后果写错**：proposal 二.2 只说"政府未给、延期或扣减，甲方**顺延**支付"。扣减不是顺延问题，而是**计费基数永久下调**问题，必须单独约定"按实收金额重新核算，已付部分适用 Clawback"。
6. **成本项开放式，乙方无法核验**："技术硬性成本"无定义，且未约定凭据与确认机制。应列举式定义 + 要求原始凭据 + 双方书面确认（或第三方审计）。
7. **模型字段存在误用风险**：`处置业务与回款` 同时列了"涉案资产变现上缴国库总额"与"政府财政拨付总金额"，但计费只用后者。应显式标注"上缴国库总额**不得**作为计费基数"，否则存在被误用为基数的解释空间。
8. **个税表述易误导**：design 五 补丁 4 写"代扣个税（20%~40%）"，属劳务报酬预扣率，未说明"次月预扣 + 年度汇算并入综合所得"，也未说明若走经营所得则为 5%~35%。附件二应写明税目、计税依据、预扣与汇算差异。
9. **自然人开票路径未定义**：乙方为自然人，"自开发票"通常需临时税务登记或税局代开；若为压低税负而将劳务报酬包装为经营所得开票，存在"变名开票"风险。应明确"税目须与业务实质一致"。
10. **增值税发票与 Clawback 的衔接缺失**：若乙方已开票、后须退还提成，红字发票冲销义务、税前/税后（已缴个税如何退回）均未约定，实操必然扯皮。
11. **保护期"自动顺延至清算完毕"与"最长 6 个月"的衔接不明**：顺延是否需要重新报备、是否触发新的确权，未写。
12. **15.5% 阶梯浮动与 SSOT 冲突**：矩阵第 2 行写"可按阶梯收益浮动商议"，但公式写死 15.5%，应给出阶梯区间或注明"公式为默认值"。
13. **存量条款溯及力问题**（见二.2）。
14. **交付物与编号映射**（见一.3、一.4）。

### 🟢 优化建议

1. proposal 四 Impact 存在**整段重复**（"市场扩展自由"两次），且一条写"华东及全国其他独立团队"、另一条写"华东及浙江省其他独立团队"，口径不一。

## 四、结论

本方案在**方向上是正确的**（背靠背零垫资、去私账去币、保追索权、留主场管辖），但**执行严谨度不足**：SSOT 在 4 处以上自我违背（Clawback 期限/范围、保护期 6 vs 3 个月、公对公 vs 自然人卡、回款主体），存在 1 处根本性架构矛盾（脱敏准则 vs 附件载明机关处室/案号 vs 公式保留 Gas 费），丢失 1 条关键合规防线（合法性前置未入正文），并有多处民事/刑事法律术语误用。这些均属**进入编码/定稿前必须收敛**的阻塞项，不能以"再打补丁"方式叠加——需先建立单一映射表，再一次性重构冲突条款。

【2. 🟡 建议改】

Y1. 计费基数扣减项不一致：proposal 二.2 为"税费、Gas费、审计费"3 项，design 公式为"直接税费 + 链上 Gas 损耗 + 司法审计与评估费 + 技术硬性成本"4 项。"技术硬性成本"无定义、无凭证要求、无上限，会被用作侵蚀乙方基数的杠杆，也与"绝对背靠背、结果确定"的立意冲突。建议改为"以双方书面确认的、有第三方票据的直接成本为限"。

Y2. 对手方所在地事实不一致：proposal 一.4 为"福建省莆田市"，design 矩阵第5行出现"福建莆田 / 河南郑州"。"郑州"无任何上游溯源，属凭空新增事实。同时矩阵"筹码"写"可在徐州泉山区法院与实际签署地法院二选一"，与 proposal"排他专属锁定徐州"不属于同一承诺档位，需在底线/筹码之间择一固化。

## 🟡 建议改

**Y1. `workbuddy_reviewer.py` 缺少 `import re`**
新增的 `re.search(...)` 未在 diff 中体现 `re` 的导入；由于整段包裹在 `except Exception: pass`，一旦缺失将**静默失效**（git status 探测彻底不生效，回落旧逻辑且无任何日志）。请确认顶层有 `import re`，并至少打印一条 fallback 原因便于排障。

**Y2. `Step0App.vue` N≥2 分支造成"版本标签漂移"**
```js
if (files.value[pairFileName]) {
  files.value[pairFileName].versionTag = res.versionTag;  // pairFileName 实为旧的生效实测回答
}
```
当采纳第 N（N≥2）版题目时，`pairFileName` 指向**旧的已生效实测回答**，却把它的 `versionTag` 改成了新题目版本号（如 QA-V2），而内容仍是 V1 的实测文本——版本号与内容不一致，后续结算/回溯会产生误读。应保持旧回答的原有版本号，或改为"旧回答归档留痕 + 新建带新版本号的空回答草稿"。

**Y3. `computeAdoptResult` 母版归档块缺显式同名守卫**
采纳"第 1 版母版"回滚时，母版归档名 `archiveV1Name` 与候选名可能相同，依赖"候选赋值发生在归档之后"才未致错，属**顺序耦合的高危写法**。请显式加 `if (archiveV1Name !== candidateName)` 守卫，消除对执行顺序的隐式依赖（断言 14 通过只是运气）。

**Y4. `activateTabInStack` 上限不收敛**
当待淘汰 Tab 全部为脏时返回 `newOpenTabs` 长度仍为 `maxTabs + 1`，仅置 `warningDirty`。用户继续打开时会持续累加、突破 6 个上限并无限增长（每次仅弹提示）。建议保持"超限即不再入栈"或提供强制确认收敛路径。

**Y5. 零 active 兜底使槽位可能无生效底牌**
`migrateAndNormalizeFiles` 新逻辑在"仅存镜像/母版"时保持零 active（仅 `console.warn`）。下游若默认存在生效底牌（如取 `activeQuestionFile/activeAnswerFile`）将取到空值。请确认 0.1/0.2 及阶段一消费端均有 null 守卫。

**Y6. 配置模块循环依赖风险**
`stage1Config.js` 新增 `import { CANONICAL_SLOT_DICT } from './config/studioArtifactConfig.js'`，而 `studioArtifactConfig.js` 侧若在模块求值期反向引用 `CATEGORY_DIR_MAP` 等，将形成 ESM 循环依赖。请确认所有交叉引用仅发生在函数体内（运行期），勿在顶层求值期互相读取。

**Y7. 残留自造词，不符合 AGENTS §3.5 文案口径**
diff 已部分把"底牌"改为"生效版本"（方向正确），但 `getActiveBadgeText` (step1) 仍返回 `客户生效底牌 …`，`[Step0App] 保存阶段零底牌…` 等注释亦保留。§3.5 明确禁止以"底牌/基线/剧本/探活"充当主文案。请全量清理为「问题清单 / 豆包答案存档 / 生效版本」。

**Y8. `smoke_step0.sh` 步骤计数一致性**
仅见 `1/5、2/5、3/5、5/5` 被修改，中间的"第 4 步"标签是否已同步为 `4/5`？请确认无残留 `4/4` 造成日志自相矛盾。

**Y9. `isProbeUnready` 以 localStorage 存在即判 ready**
只要浏览器本地存有阶段零文件就绕过 `probe_status` 门禁，语义上"本地有草稿 = 已探活"。这在换机/清缓存场景会前后不一致，且可能使未真正探活的项目通过。属产品口径变更，建议收敛为"存在 **active 生效问答** 且与后端 status 一致"。

**Y10. `computeSaveResult` 未拦截 `content === null`**
仅拦截 `undefined`；`null` 会走非空守卫判定为无效，对 active 返回 EMPTY_CONTENT 尚可，但**非 active 文件会把 `content: null` 落盘**。建议统一 `content == null` 拦截。
