# Review Log: 阶段零问答采纳标注与血统溯源标识

## 1. Grill 深度盘问实录与共识裁决 (2026-09-27)

### 决策点 1：采纳标注的颗粒度 [已达成共识]
- **问题**：在阶段零有多份题目与回答时，应该以哪种方式明确“给客户使用的是哪套问题与答案”？
- **选项**：
  1. (Recommended) 采用【整份文件采纳】模式：在文件树和编辑器打上【当前采纳】徽章，一键将当前提问清单和实测回答绑定并设为唯一底牌，下游直接以此为准；
  2. 采用【单题拆分勾选】模式；
  3. 采用【整份文件生效 + 题项目录清单】模式。
- **裁决结论**：采纳选项 1。保持整份文件作为打磨与采纳颗粒度，最贴合专家在 IDE 式文本工作台中的高频编辑体验，避免打碎为卡片带来的繁琐交互。

### 决策点 2：一环扣一环的链路标识（溯源血统戳） [已达成共识]
- **问题**：关于“什么结果出什么报告”的一环扣一环标识（链路溯源身份证），我们该如何设计？
- **选项**：
  1. (Recommended) 方案 A：统一版本号血统戳（如【QA-V1】或【基线-01版】），提问、回答与下游报告头部均印上此戳，重命名不丢引用，机器精准索引；
  2. 方案 B：直接按文件名引用；
  3. 方案 C：双轨制。
- **裁决结论**：采纳选项 1。使用 `QA-V1`、`QA-V2` 统一血统戳，解耦物理文件名，防范文件重命名后链路断裂的问题。

### 决策点 3：问答绑定与血统戳生成生效节点 [已达成共识]
- **问题**：【问答绑定与血统戳生效节点】应该在操作动线的哪个环节自动完成？
- **选项**：
  1. (Recommended) 方案 A：0.1 题目确认采纳时生成【QA-V1】，0.2 贴回答时自动继承该版本号；0.2 点【完成并存底牌】时正式封版生效；
  2. 方案 B：在 0.2 点【完成阶段零并存入底牌】的一瞬间打上；
  3. 方案 C：弹窗确认模式。
- **裁决结论**：采纳选项 1。前置在 0.1 确定题目，0.2 顺畅继承，0.2 封版完成阶段零，动线自然顺滑无额外打扰。

### 决策点 4：版本切换与互斥原则 [已达成共识]
- **问题**：如果项目里已有生效底牌【QA-V1】，后来专家打磨了新题目并点击【设为当前采纳】，系统如何处理新旧版本？
- **选项**：
  1. (Recommended) 方案 A：单底牌互斥原则：当专家把另一份新文件设为当前采纳时，旧文件自动取消【当前采纳】变为历史，新采纳版本号自动递增为【QA-V2】；
  2. 方案 B：版本锁定覆盖；
  3. 方案 C：自选版本号。
- **裁决结论**：采纳选项 1。保证全案有且仅有一套生效底牌，切换时版本号自增，历史记录依然留存可追溯。

### 三、本轮新发现的问题

#### 🟡 问题 1：采纳记录指向的文件在刷新后丢失，导致溯源章引用不存在的文件名

**实测证据链**：

```
1. localStorage 记录：activeQuestionFile = "01_豆包题目_第2版.txt"
2. 但左栏文件树中【不存在】该文件，只有 "01_豆包提问清单_推荐版.txt"
3. 界面兜底逻辑生效：把 "01_豆包提问清单_推荐版.txt" 标为「已采纳 [QA-V2]」
4. 阶段一溯源章仍写：（01_豆包题目_第2版.txt + 02_豆包实测回答记录_初测.txt）
   → 引用了一个当前并不存在的文件名
```

**根因分析**：

- 阶段零 `handleRefreshQuestions` 生成的**新题目文件只存在于内存**（阶段零未做文件内容持久化，
  与阶段一不同 —— 阶段一有 `geo_step1_state_*`）；
- 页面刷新后 `initDefaultFiles` 重建为初始 2 个文件，新版本文件消失；
- 但采纳记录 `geo_step0_active_qa_geo` 被保留，`activeQuestionFile` 仍指向已消失的文件；
- 加载兜底时**只把推荐版标记为 `isActive`，未同步修正 `activeQuestionFile`**，
  导致「界面显示的采纳文件」与「记录/溯源章引用的文件名」不一致。

**影响**：溯源章的可信度受损 —— 交付物上印着一个找不到出处（文件不存在）的名字，
与「血统溯源」这个功能的初衷相悖。

**修复建议（二选一）**：
- **方案 A（推荐）**：加载时校验 `activeQuestionFile` 是否存在于当前 `files` 中，
  不存在则**回退并同步修正**记录为兜底文件（保持记录与界面一致）；
