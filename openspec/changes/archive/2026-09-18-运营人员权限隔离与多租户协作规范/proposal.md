# Proposal: 运营人员权限隔离与多租户协作规范

## Why (为什么做)
随着 GEO 系统由单兵作战工具升级为团队协作平台，需要多位同事共同参与日常运营工作（如录入关键词、触发 AI 内容生成流水线、在线润色和校对文章、查看效果预览与评分报告）。
然而，目前系统处于单一管理员模式，缺乏细粒度的权限控制。如果直接将管理权限放开给同事，可能导致以下严重隐患：
1. **生产误操作风险**：运营人员可能误点“推生产上线”或“全站重编译”，导致线上在售客户网站出现事故。
2. **多租户数据泄露**：同事可能跨越自身负责的客户站点，随意查看或改动其他客户的核心数据。
3. **架构失控**：系统设置、环境配置和人员授权如果缺乏统一管控，会导致职责不清。

**核心铁律（师弟定稿）**：
- **开发人员只有师弟一个人**：全系统有且仅有师弟拥有最高开发与管理特权（成员授权、系统配置、生产部署）。
- **其他所有人都是运营人员**：所有同事一律归入“运营”角色，**只有使用权限，完全没有管理权限**；且其管辖范围严格隔离至被分配的具体客户项目。

## What Changes (改动了什么)
1. **确立“唯一开发 + 隔离运营”的双层角色模型**：
   - **开发者（Developer）**：全平台唯一超级管理员，负责平台全局配置、成员开通与权限划定、代码与生产部署发布。
   - **运营人员（Operator）**：纯使用者角色，无任何管理权限，按项目管辖范围和细化功能权限开展业务。
2. **构建轻量本地 RBAC 数据中心**：
   - 在 GEO 系统内建立轻量、透明的成员花名册存储（`data/rbac_members.json`），记录被授权同事的手机号、姓名、管辖项目（`allowed_projects`）以及运营权限清单（`permissions`）。
3. **后端 API 严格鉴权与防越权卡点**：
   - 结合小毛驴统一登录返回的手机号，校验用户在 GEO 系统中的角色与项目管辖权。
   - 关键敏感接口（推生产部署、成员增删改查、底层环境设置）强制绑定 `require_developer` 拦截，非开发者一律返回 403 Forbidden。
   - 业务接口（词库、文章编辑、AI 流水线）根据用户授权的 `allowed_projects` 和功能权限进行阻断校验。
4. **前端工作台自适应安全裁剪**：
   - 运营人员登录后，项目切换下拉框仅展示其被分配的客户项目，彻底屏蔽未授权租户。
   - 界面自适应隐藏/移除“成员管理”、“系统设置”、“推生产上线”等高危管理功能，严防误触。
   - 为开发者提供专属的“成员管理”控制面板，支持一键录入同事手机号、指派项目与勾选业务功能权限。

## Capabilities (新增或修改的对外能力)
1. **开发者专属管理接口**：
   - `GET /api/admin/members`：获取全量协作成员列表及权限配置。
   - `POST /api/admin/members`：新增运营人员（输入手机号、姓名、管辖项目列表、权限清单）。
   - `PUT /api/admin/members/<phone>`：修改运营人员管辖项目或功能权限、启用/停用账号。
   - `DELETE /api/admin/members/<phone>`：移除协作成员。
   - **订正说明**：原提案中的 `/api/admin/deploy` 在代码库中**并不存在**（`tools/geo/server.py` 全量检索 `deploy` 命中 0 次）。按 `AGENTS.md` 第 4 节，生产发布是人工单行命令 `ssh mini "cd /Users/ne/apps/GEO && git pull github main"`，不落 Web API。因此**本期不新增部署接口**，改为把已有的高危写操作纳入开发者专属清单（见下条）。
2. **运营人员细分功能权限矩阵**：
   - `keyword:manage`：关键词词库导入、编辑与导出。
   - `ai:generate`：触发 AI 语料提纯、文章生成与 FAQ 生成流水线。
   - `article:edit`：在线查看、编辑并保存文章与案例。
   - `preview:view`：查看当前负责站点的本地渲染效果。
   - `report:view`：查看 GEO 诊断打分与分析报告。
3. **前置拦截机制**：
   - 未在系统花名册授权的手机号登录后，提示“您尚未获得 GEO 平台操作权限，请联系管理员开通”并安全退出。
4. **服务端统一路由守卫（本期新增，取代逐接口埋点）**：
   - 现状：`tools/geo/server.py` 共 **237 个 API 路由分支**，其中约 180 个为 `/api/projects/{id}/...` 项目级接口，全部在 `check_auth()` 之后裸奔，**无任何项目级或权限级校验**。
   - 方案：在 `do_GET/do_POST/do_PUT/do_DELETE` 的统一入口处加一层路由守卫，按「公开白名单 / 开发者专属 / 项目级 / 需原子权限」四档集中判定，禁止在 200+ 个分支里逐个 `if` 埋点。
5. **服务端数据过滤（安全边界在服务端）**：
   - `GET /api/projects` 与 `/api/groups` 必须按 `allowed_projects` 在服务端过滤后再返回；前端下拉框过滤只是体验优化，**不是安全边界**。
