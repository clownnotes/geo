# Proposal: 工作台三场景信息架构重排

## Why (为什么做)

1. **功能全在，但前端无法判断「今天该点哪个」**  
   现有 5 步流水线本身正确，但每步标题旁（尤其第 4、5 步）把「交付主路径 / 进阶武器 / 运维报表」摊成同级彩色按钮墙；仪表盘顶栏还有 18–26 号工具 pill 再铺一层。新人打开项目会眩晕，交付节奏被打乱。

2. **业务真实有三种完全不同的用法**  
   - 刚进客户：要快速跑通「测算 → 建站 → 母盘 → 发稿 → 首轮监测」；  
   - 5 步之后：要二次打分、打竞品、补检索与护城河；  
   - 客户续费运维：要看周报、分享链接、巡检台账与危机排查。  
   这三件事混在同一按钮密度下，版面必然乱。

3. **对标小毛驴管理台的成熟分抽屉思路**  
   小毛驴「模型管理 / 套餐配置 / 用量统计」按「我现在要干什么」分大 Tab，而不是按技术模块堆按钮。本次把同一原则落到 GEO 向导：先场景，再步骤/主题组。

## What Changes (改动了什么)

1. **向导顶层新增三场景 Tab**  
   `初步交付 | 二次提升 | 日常维护`；默认进入「初步交付」。不删任何既有 Modal / JS 业务函数，只换入口归位。

2. **场景一：初步交付（保留 5 步，裁剪主路径）**  
   - 第 1 步定名为「测算诊断」，主路径只留执行体检 + 报告预览；  
   - 第 2–3 步每步主路径不超过约 3 个显眼操作；  
   - 第 4 步发稿卡定型为：生成包 + 一键复制主文 +「更多」折叠（附属文案 / Clean MD / 后台链接）；四色摘要小卡改为进度跳转条；  
   - 第 5 步主路径只留：声量监测、导出周报、结案验收单。

3. **场景二：二次提升（按 4 个主题组挂入口）**  
   竞品与护城河 / 检索与内容增益 / 信源与归因加深 / 对抗与鲁棒；售前 Pitch 不进交付主路径。

4. **场景三：日常维护（运维固定动作）**  
   给客户看的（分享链接、周报、证书、ZIP）/ 每周巡检（监测、Citation 对账、台账探活、半衰期）/ 危机与声誉 / 普林斯顿复检。

5. **仪表盘顶栏按钮墙同步收口**  
   顶栏 18–26 号等工具 pill 迁入对应场景，避免列表页与向导双重按钮墙。

## Capabilities (新增或修改的对外能力)

| 能力 | 说明 |
|------|------|
| 场景切换壳 | 向导内 `switchScene('delivery'\|'boost'\|'ops')`，三面板互斥显示 |
| 交付主路径瘦身 | 5 步每步主 CTA 清晰；发稿卡「更多」折叠 |
| 二次提升主题架 | 4 组卡片承载全部进阶 Modal 入口 |
| 日常维护工作台 | 客户可见物 + 巡检 + 危机 + 复检入口集中 |
| 能力零丢失 | 所有原 `open*Modal` / 复制 / 打包函数可从新入口触达 |

本变更**不新增后端 API、不改流水线阶段语义、不删业务能力**；纯前端信息架构与 DOM 归位。

## Impact (受影响的部分)

- 主要文件：[`web/index.html`](../../../web/index.html)（向导 header、步骤面板、仪表盘顶栏、新增 boost/ops 面板与 `switchScene`）
- 不改：`tools/geo/server.py`、各 `tools/geo/*.py` 业务引擎、既有 Modal DOM 与 JS 实现
- 视觉：严禁新增 Emoji；企业风靠 Tag / 字阶 / 分组卡片
- 测试范围：本地 `http://127.0.0.1:8088`；严禁私自推生产
- 协同：需跨 IDE 在 `review-log.md` 对齐入口归属表后再 `/opsx-apply`
