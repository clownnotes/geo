# Design: 对照苍何诊断与答题卡母盘的交付提升探讨

## Context

- 苍何 Skill：4 阶段诊断（基建/可见性/舆情/评分）→ JSON → HTML；大量「虚拟收录」。
- 邻里GEO：工程交付 0～5 步 + 真实侦察/发稿/监测；售前有 pitch，但不是同构的「诊断专家报告」。
- 产品口述强调：交叉选词、答题卡覆盖、母盘建库、双站、月验约 100 次。

## Goals / Non-Goals

**Goals**

- 把对照结论与 U1～U10 写成可讨论的规范真源。
- 先澄清答题卡 vs 母盘，避免团队和客户听混。
- 探讨三个拍板问题（诊断形态 / 100 次是否标配 / 双站定义）。

**Non-Goals（本变更）**

- 不实现完整 AIVO HTML 诊断流水线。
- 不把管理台五步改成「苍何 7 步」重命名游戏。
- 不把虚拟提及率包装成实测。

## Architecture（文档层）

```
对照材料 ──► geo-flow-benchmark-canghe.md（映射 + U 清单）
                │
                ├── answer-card-vs-master.md（U1）
                └── roadmap-2026.md 欠账 B～…（U2～U9 挂账）
                        
探讨共识后 ──► 另开 OpenSpec apply（按勾选的 U 项）
```

## Decisions to make in review

| ID | 问题 | 选项草案 |
| :---: | :--- | :--- |
| D1 | 诊断报告放哪 | A 阶段一升级 / B 独立售前产品 / C 仅人工+模板 |
| D2 | 月度采样 | A 合同标配约 100 次 / B 按套餐分级 / C 维持现有周报样本量 |
| D3 | 信息发布站 | A = 现有托管 `sites/{id}` / B 另做发布型站点产品 |

## Risks

- 过度对齐苍何的「虚拟搜索」会削弱我们「真实豆包侦察」差异化 → 用 U7 卡住。
- 欠账一次开太多 → 探讨只勾 1～2 个下一迭代。
