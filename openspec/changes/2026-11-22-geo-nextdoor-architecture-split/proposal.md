# Proposal: GEO 与小毛驴双工作区分工规则及后厂接口整肃方案

## 核心原话实录（第一真理源）

> **师弟原话（工作台定位与双轨业务 · 2026-11-22）**：
> “GEO 项目整体架构设计。结合现在沟通过的架构设计。我们主要包括外包记账和自研日常维护两个版块。……我们的场景，主要是自己使用，自己来维护实体客户。我思考是，这个就像是一个工作台。能够引导人把每一步 SOP 做好。”

> **师弟原话（数据库与开源底座判断 · 2026-11-22）**：
> “我在实践中发现，有数据库的重型开发，反而正确率会更高。原因可能是因为数据库开发，有更多的框架标准 AI 不能够随意设计，反而更好。……我准备做的很长远。未来可能要经常改，经常优化。也会加入更多后厂的产品进来。而且里面比如调用本地模型这些，我准备复用小毛驴，这些条件下来，是不是复用小毛驴的框架设计比较好？”

> **师弟原话（整肃方向与立规先行 · 2026-11-22）**：
> “我都是用反重力开发。所以第一步，是不是应该这样做？需要一份工作区的规则，来记录这个工作区和小毛驴工作区做 GEO 开发的分工说明。同时也要让小毛驴工作区，对应文件夹，比如数据库，GO，VUE 前端这些知道。怎么跟 GEO 工作区配合。……我觉得也不用过渡期铁律了。下一个规范就是按照我们定的架构，开始整肃以前的代码了。”

---

## Why

当前 `GEO` 仓库采用 1.18 MB 单文件 `src/web/index.html` 配合散装 JSON/YAML 纯文件持久化，存在前端易改坏、纯文件缺乏字段强约束、无法直接复用小毛驴（Nextdoor）本地模型与统一权限底座的问题。随着业务确定长期演进并纳入“前店后厂”统一体系，必须彻底确立“小毛驴管前店业务与数据库、GEO 管后厂专业计算与静态站资产”的清晰边界，先立双边协作规则与接口契约，再据此整肃存量代码。

---

## What Changes

1. **确立双工作区“前店后厂”分工与协作规则**：
   - **小毛驴工作区（`/Users/a1/next核心项目`）**承担前店与大管家职责：Vue 3 管理端工作台（XiuLan_IDE 四级导航）、Go 核心后端（`Handler -> Logic -> Repository -> Model`）、关系型数据库（唯一业务真相源）、账号权限、雪花 ID 与本地模型调度；
   - **GEO 工作区（`/Users/a1/代码/GEO`）**定位为纯后厂专业车间：只保留并提纯 Python 无状态计算引擎（爬虫体检、大模型采样、静态官网建站、博客与 `llms.txt` 生成）及客户成品站点/资料仓（`projects/{id}/outputs/`、`GEOZiLiao`）；
   - **取消过渡期并存**：明确整肃方向，不再在 GEO 仓库新增管理端界面、业务状态 JSON 或数据库表。
2. **明确双边 4 处规则文件的更新方案（人机联动确认后落盘）**：
   - 更新 `GEO/AGENTS.md`，声明后厂定位、淘汰老管理台红线与对外接口契约；
   - 更新小毛驴 `AGENTS.md`、`02_管理员操作端/XiuLan_IDE/RULES.md`、`04_统一大后端代码/统一后端-Go/RULES.md`，明确 GEO 模块的 Vue 路由位置、Go 表前缀与分层调用方式、禁止前端直连 Python。
3. **定义 GEO 后厂 Python 无状态工具接口契约与整肃清单**：
   - 将 `src/tools/geo/` 中有价值的专业能力收敛为无状态 HTTP Worker 接口（官网诊断、问答采样、静态站生成、博客索引构建）；
   - 列出存量待淘汰清单（1.18 MB `src/web/index.html`、旧管理台路由、散装记账 JSON 逻辑）与数据迁移路径。
